# kemi 仕様: 読み進める操作

[kemi 仕様](kemi.md) の一部。グループ単位の切り替え、由来、変更間の移動、見たと進捗、コメントと suggestion、重要の表示。
用語の定義は `CONTEXT.md`、成功条件と反例の書き方は [kemi 仕様](kemi.md) の冒頭にある。

---

## R-UNIT グループ単位の切り替え

コミット範囲の「最終形」と「コミットごと」を、1 回の起動の中で切り替える。

**要件**

- 切り替えはコミット範囲モードにだけ出す。コミットが 1 つだけの範囲でも出す。
  manifest / worktree / staged には出さない。
- 起動時は `--group-by` の単位（既定 最終形）だけを作る。もう片方は `api/review` の
  最初の応答を返した後、裏ですぐ作り始める。切り替えた時点で未完成なら読み込み中と
  表示する。作るのに失敗したときは、切り替えを「作れなかった」表示（理由と再試行の
  操作付き）にしてレビューを続ける。この失敗ではレビューを終了コード 2 で終えない。
- 作った単位は作り直さず、切り替えは表示の差し替えだけにする（ライブリロードは
  除く、`R-LIVE`）。
- コミットごとの単位を作るときは git の呼び出しを並列にしてよい。並列度は D8。
  並列で作っている間も、表示中のファイルの取得（`api/file`）は 100 ms 以内に返す
  （範囲の標準フィクスチャ、開発機でのスモーク基準）。
- 見たはグループ単位ごとに別に持つ。最終形で見たを付けても、コミットごとの同じ
  パスのファイルは未読のまま（`R-SEEN`）。
- コメントは、付けたグループ単位のファイルにだけ表示する。submit JSON には両方の
  単位のコメントがすべて作成順で入り、`group_id` で区別する（最終形は `all`）。
  切り替えても、前の単位で付けたコメントは消えず、`outdated` にもならない
  （グループ単位の切り替えでは `outdated` は変わらない。`R-COMMENT`）。
- 単位を切り替えたときは同じパスのファイルを表示する。コミットごとへ切り替えた
  ときは、そのパスを含む最初のコミットのファイルにする。同じパスが無ければ先頭の
  ファイルを表示する。由来から移ったときは、そのコミットの同じファイルの該当行を
  表示する（`R-ORIGIN`）。

**成功条件**

- 200 コミット × 100 ファイルのフィクスチャ（`R-VERIFY`）で、コミットごとの単位を
  作る時間が 1 秒未満（release ビルド、`scripts/measure-range.sh` の `commit`、
  3 回の中央値）。開発機のスモーク基準で、扱いは `R-SERVE` の 1 秒と同じ。
- 最終形とコミットごとの両方でコメントを付けて submit すると、両方のコメントが
  入り、`group_id` がそれぞれ `all` とコミットの sha になる。
- 最終形で見たを付けたパスが、コミットごとでは未読のまま。
- 単位を切り替えて戻っても、コメントと見たが残る。
- 範囲の標準フィクスチャで、裏でコミットごとの単位を作っている間の `api/file` の最も遅い
  応答が 100 ms 未満（`scripts/measure-range.sh` の `busy`）。
- コミットごとの単位を作るのに失敗しても（例: 作成中に `--to` の ref が消える）、
  レビューが続き、切り替えに「作れなかった」表示が出る（人が確認）。
- manifest / worktree / staged のページに切り替えが出ない。

**反例**

- 切り替えると、前の単位で付けたコメントが消える、または `outdated` になる。
- 最終形で起動したのに、コミットごとの単位を作り終えるまで最初の表示が出ない。
- 切り替えのたびに単位を作り直して待たされる。
- 裏での作成の失敗で、読んでいる途中のレビューが終了コード 2 で終わる。

## R-ORIGIN 由来

最終形の各変更ブロックに、その変更を入れたコミットを示す。

**要件**

- 最終形の各変更ブロックのすぐ上の「由来の行」（`R-VIEW`）に由来を出す。由来は、
  そのブロックの新側の行を最後に変えた、範囲内のマージ以外のコミットすべてを、
  新しい順に、短い sha と件名で示す。新側の行のうち、範囲内のどのコミットにも
  マージにも当たらない行が一部あれば、見つかったコミットに「一部特定できない」を添える。
- 削除だけの変更ブロックは、消えた行ごとにその行を消したコミットを求め、見つかった
  コミットをすべて新しい順に出す。1 行でも決まらない行があれば「一部特定できない」を
  添え、1 行も決まらなければ「特定できない」とだけ出す。消したコミットは
  `git blame --reverse` 相当で辿る。横のブランチで消した行がマージで入った場合は、
  マージではなく、そのブランチで消したコミットを由来にする（マージのもう片方の親の
  側を、マージ基点から辿り直す）。この辿り直しはマージの入れ子 8 段までとし、それを
  超えた行と辿れない行は「特定できない」に数える。
- 由来の「範囲」は、コミットごとの単位と同じ `--from..--to` のマージ以外のコミット
  とする。範囲内のどのコミットにもマージにも当たらない行は、由来の無い行として数える
  （ブロックの一部なら「一部特定できない」を添え、全部なら「特定できない」とだけ出す）。
- マージ自体（衝突の解決）が変えた行・消した行は、由来に「マージ `<短い sha>`」と出す。
- 由来を押すと、そのコミットの理由（本文）が開く。コミットの由来には「このコミットで
  見る」操作を付け、コミットごとの単位の、そのコミットのグループへ移る（`R-UNIT`）。
  移り先の行は `git blame` が示す、そのコミット時点のパスと新側の行番号とし、削除
  だけのブロックでは、そのコミットの旧側の行とする。マージの由来は理由を開くだけで、
  移り先は持たない。
- 由来はファイルを表示した時に計算する。差分の表示は由来の計算を待たず、由来は
  計算できたものから後から付く。
- 1 ファイルの片側が 10,000 行超または 1 MB 超のときは由来を既定で出さず、
  そのファイルでだけ有効化できる（ハイライトと同じ上限）。
- 由来の計算に失敗したファイル（git の失敗など）は、そのファイルの由来の行に
  「特定できない」と出し、レビューは続ける。この失敗ではレビューを終了コード 2 で
  終えない（`R-SUBMIT`）。

**成功条件**

- 2 つのコミットが同じファイルの別の箇所を変えたフィクスチャで、各変更ブロックの
  由来がそれぞれのコミットになる。
- 1 つのコミットが行を消したフィクスチャで、その削除だけの変更ブロックの由来が
  そのコミットになる。
- 横のブランチで行を消し、それをマージで取り込んだフィクスチャで、その削除だけの
  変更ブロックの由来がマージではなくそのブランチのコミットになる。
- 新側の行の一部が範囲内のどのコミットにも当たらないブロックで、見つかった
  コミットに「一部特定できない」が添えられる。
- 範囲の途中で改名されたファイルで、「このコミットで見る」が、そのコミット時点の
  パスの該当行へ移る。
- 範囲より前のコミットや、範囲外のコミットが由来に出ない。
- 10,000 行超のファイルで由来が出ず、有効化すると出る。
- 由来の計算で git が失敗するファイルを表示しても、そのファイルの由来が「特定できない」に
  なり、レビューが続いて、付けたコメントを submit できる。

**反例**

- 由来の計算が終わるまで差分が表示されない。
- 起動時に全ファイルの由来を計算する。
- 由来を特定できない削除ブロックに、推測したコミットが断定として出る。
- 途中で改名されたファイルで、「このコミットで見る」が別のファイルや別の行へ移る。
- 1 ファイルの由来の計算の失敗で、レビュー全体が終了コード 2 で終わり、コメントが失われる。

## R-NAV 変更間の移動

**要件**

- 描画表示（`R-RENDER`）では、変更の印の付いたブロックの先頭と、コメントの札の
  位置（置き場は `R-RENDER`）を止まる場所とする。以下の規則はソース表示のもので、
  由来の行の括弧は描画表示には効かない。
- ファイルを飛ばすかどうかは、そのとき見ている表示モードではなくソース表示の止まる場所で
  決める。そのため、既定が描画表示の SVG（`R-RENDER`）のように描画表示の止まる場所が
  0 になるファイルへも移り、移った先ではファイルの先頭を見せる。そこで続けて `n` を
  押すと次のファイルへ進む。
- 変更ブロック（`CONTEXT.md`）とコメントの位置を「止まる場所」とする。止まる場所は、
  変更ブロックの先頭（最終形で由来の行があるときは、その由来の行）と、変更ブロックの外にある行
  コメントの範囲の最初の行。範囲の最初の行が変更ブロックの中にあるコメントは、その
  ブロックの先頭で一緒に止まったものとする。ファイル全体へのコメントは止まる場所に
  含めない。
- 差分の右下に「前の変更」「次の変更」の操作と、表示中のファイルの止まる場所の
  「現在 / 全体」の数を常に出す。キーは `n`（次）と `p`（前）。文字の入力欄に
  フォーカスがある間は、`n` / `p` / `v` を含むキー操作は働かない。
- 「現在」は、表示領域の上端から少し下に引いた基準線（距離は実装が決める）を最後に
  越えた止まる場所とし、移動の記録ではなく、そのときの表示の状態から毎回決める。
  上端が基準線とちょうど同じ止まる場所は、越えたものとして数える。
  末尾までスクロールしきってそれ以上進めないときは、見えている止まる場所をすべて
  通過済みとみなし、「現在」はそのファイルの最後の止まる場所になる。どの経路で
  末尾に達しても同じで、そこで `n` を押すと次のファイルへ移る（最後のファイルでは
  "This is the last change"）。`p` は、そこへ送ると実際に表示が上へ戻る止まる場所のうち
  最後のものへ移り、どれも戻らなければ前のファイルの最後の止まる場所へ移る（最初の
  ファイルでは "This is the first change"）。ファイルの途中では、これは現在の 1 つ前と同じ。
- 表示中のファイルの最後の止まる場所で `n` を押すと、次のファイルの最初の止まる
  場所へ移る。「次のファイル」はツリーに見えている順（変更量順の並べ替えと重要のみの
  絞り込みを反映し、グループをまたぐ）で決める。ツリーで畳まれたグループや
  ディレクトリの中のファイルも順に含め、移ったらツリーをそこまで開く。ノイズとして
  畳まれたファイル、バイナリ（`R-RENDER` の画像を含む）、止まる場所が 1 つも無い
  ファイル（改名だけなど）は飛ばし、見たのファイルは飛ばさない。最後のファイルの最後の止まる場所では移らず、"This is the last change" と出す。
  `p` はこれと対称で、最初のファイルの最初の止まる場所で "This is the first change" と出す。
- スクロールバーの横に、表示中のファイルの変更（追加・削除の色）とコメント
  （コメントの色）の位置を示す細い帯と、今見えている範囲の印を出す。帯を押すと
  その位置へ移る。コードの縮小表示はしない（`P3`）。

**成功条件**

- 止まる場所を求める純粋関数のテストで、変更ブロックの先頭、ブロック外のコメント、
  ブロック内のコメント、ファイル全体のコメントの扱いが上のとおりになる。
- 「現在」と `n` / `p` の移り先を求める純粋関数のテストで、ファイルの途中、末尾まで
  スクロールしきった状態、スクロールできない短いファイル、基準線ちょうどにある
  止まる場所の扱いが上のとおりになる。
- 最後のファイルの最後の止まる場所で `n` を押すと、移らずに "This is the last change" と
  出る（人が確認）。
- 50 万行のフィクスチャファイルで、帯の表示と `n` / `p` を使ってもスクロールが
  固まらない（人が確認。`R-VIEW` の条件に含める）。

**反例**

- `n` が最後の変更から先頭へ戻り、どこまで読んだか分からなくなる。
- 帯がファイル全体の行を DOM に描いて、50 万行で固まる。

## R-SEEN 見たと進捗

**要件**

- 見たは、ファイルヘッダの文字付きのチェック "Seen" とキー `v` で付け外しする。
- 「閲」の印を出すのは、グループのファイルをすべて見たとき（ツリーのグループ見出し）
  と、承認の完了画面だけ。ほかの場所では使わない。
- ツリーのファイル行は、左端のチェックで見たかどうかを示す。取り消し線は使わない。
- ツリーのグループ見出しに「見た数 / 全数」と進捗バーを出す。グループのファイルを
  すべて見たら、数の代わりに「閲」の印を出す。
- 上部に、表示中のグループ単位の全体の進捗（見た数 / 全数）を出す。
- 見たはグループ単位ごとに別に持つ（`R-UNIT`）。

**成功条件**

- グループのファイルをすべて見たにすると、そのグループ見出しに「閲」の印が出る
  （人が確認）。
- `v` で表示中のファイルの見たが切り替わり、ツリーと上部の進捗が同時に変わる
  （人が確認）。

**反例**

- グループのファイルをすべて見ても、グループ見出しが変わらない。
- 見たのファイル名が取り消し線で表示され、削除されたファイルと区別できない。

## R-COMMENT コメントと suggestion

説明対象と引用・outdatedは [R-EXPLANATION-COMMENT](explanation.md#r-explanation-comment-対象と更新後の会話) を適用する。

**要件**

- コメントは行レンジ（左右どちらかの連続した行）またはファイル全体に付けられる。
  ファイル全体のコメントは行を持たない。描画表示（`R-RENDER`）から付けたコメントも、
  そのブロックの元の行レンジへの行コメントで、この節の規則と submit JSON の形は変わらない。
- 行番号は 1 始まり、両端を含む。旧側の行番号は旧ファイルの行番号を指す。
- 解決（resolve）と返信は画面から行える。返信は人間もエージェントも書け、解決は人間だけが
  行える（[agent-channel.md](agent-channel.md#r-agent-hand-渡す)）。
- `--live` のページへのコメントは、行レンジの代わりに要素・矢印・ペンの場所を持つ
  （[live.md](live.md#r-page-comment-コメントの場所)）。
- コメントにはファイル内容の変化に対する `outdated` 状態がある:
  - コメント作成時の行テキスト（`quote`）と、対象ファイルの内容ハッシュを保持する。
  - 内容ハッシュが変わっていたら「古いコメント」として表示する。
    **自動で行番号を付け替えはしない。**
  - 履歴の書き換えでコメントを付けたグループが消えたときも「古いコメント」とする
    （`R-LIVE`）。
- suggestion は「新側の行レンジを置換する文字列」として構造化して保持する。
  空文字は行の削除を意味する。挿入のみの提案は、隣接行を含む置換として表現する。
  **suggestion は新側の行コメントにだけ付く。旧側とファイル全体のコメントでは
  常に `null`。**
- suggestion をブラウザから適用する機能は持たない（`P8`）。受け取った JSON を
  使って適用するのはエージェントの仕事。
- コメントは編集と削除ができる。
  - 編集で変えられるのは本文と suggestion（新側の行コメントだけ）。行レンジ・
    `side`・`quote`・作成時の内容ハッシュ（`outdated` の判定基準）は変えない。
    行レンジを変えたいときは、削除して付け直す。
  - 削除は確認を 1 回挟む。削除したコメントは submit JSON に出ない。コメントの
    `id` は再利用しない。
- コメントが追加されたとき、人間向けのライブ表示を stderr に出す。
  行の頭の `kemi: comment ` は変えない（エージェントがこの行を見分けて読み飛ばすため）。
  それより後ろの文言は契約としない。

**成功条件**

- コメントを付けて submit すると、`R-SUBMIT` の JSON に、本文・解決状態・
  `quote`・`outdated`・suggestion・返信が入っている。
- コメント後にファイルを変更して submit すると、そのコメントの `outdated` が
  `true` になる。
- 旧側（削除された行）にコメントでき、その suggestion は `null` になる。
- 本文を編集して submit すると、編集後の本文が入り、行レンジと `quote` は作成時の
  まま。
- 削除したコメントが submit JSON に無く、その後に付けたコメントの `id` が削除した
  `id` と重ならない。

**反例**

- suggestion が自由文に埋め込まれ、機械的に適用できない。
- 内容が変わったのに古い行番号のまま最新の行として提示される。
- 編集で行レンジや `quote` が変わり、エージェントが元の位置を特定できなくなる。
- 削除したコメントが submit JSON に残る。

## R-FOCUS 重要の表示

kemi は重要度を推定しない。重要の印は実装したエージェント（manifest または
`--focus`）が付ける。kemi はそれを優先的に見せるだけだ。

**要件**

- `focus: true` のファイルにはバッジと `note` を表示する。
- グループの `watch` を "Watch" のラベルでグループ見出しに常に強調して表示する。
  `why` は見出しの下に畳んで置き、開ける（`R-VIEW`）。
- 「重要のみ表示」のフィルタは、ツリーのファイルを絞る（本文の表示は変えない）。
- kemi が自動で並び順や重要の印を変えることはない。人が変更量ソートのトグルを
  操作した時だけ並びが変わる。
- ファイルツリーと `R-DIGEST` にも `focus` を反映する。

**成功条件**

- `focus` を付けたファイルにバッジとノートが出て、フィルタで絞り込める。
- 変更量だけを理由に順序や印が自動で変わることはない。

**反例**

- kemi が変更量や拡張子から「重要そう」なファイルを自動で重要扱いする。

## 作らないもの

- P3 ミニマップ（コードの縮小表示）。変更とコメントの位置の印だけを並べる帯
  （`R-NAV`）は作る。
- P8 suggestion のブラウザからの適用。適用はエージェントが行う。
- P9 LLM がコメントを立てる機能。返信・発言・案はライブ改訂で書けるようにした。件数の上限は
  [agent-channel.md](agent-channel.md#r-agent-write-reply-の入力と上限) の契約。

## 委譲

- D8 コミットごとの単位を作るときの git 呼び出しの並列度。どの値でも表示される内容は
  同じで、`R-UNIT` の時間条件と「表示中の操作を遅らせない」を計測しながら満たす値を
  実装が探る。

## 却下

- R6 suggestion のブラウザ適用（理由: 自分では直さない方針）。
- R7 ツールを変えず、旧 `diff-review-viewer` スキルに `--group-by file` か manifest を使わせるだけにする
