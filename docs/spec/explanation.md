# EXPLANATION 仕様

- Status: 承認済み。承認対象は `55ba772` の三文書の契約本文と、その後に加えた読む画面（R-EXPLANATION-READING）と選択引用（`selection`）の改訂。
- 承認対象: この文書、[共通パーツ](content-parts.md)、[既存契約の改訂候補](explanation-contracts.md)の一組。
- 現行契約: [kemi.md](kemi.md)、[agent-channel.md](agent-channel.md)、[live.md](live.md)。変更する節は改訂候補に列挙する。
- 前提: 利用者から渡された確定事項と承認済み計画に基づく。実装状況はコードと実装計画で確認する。

EXPLANATIONは、コードと画面を横断してレビュー全体を説明する場所である。
説明の内容、読む順、全体・前提・個別の粒度は作成するLLMが決める。
kemiは理解度を推定せず、三つの章を必須にしない。

## 用語の追加候補

用語の読みの正典は `CONTEXT.md`。以下は説明契約で使う語の対応表。

| 語 | この草稿での意味 |
|---|---|
| 説明 | レビュー全体に一つある、見出しとID付き説明ブロックの列。UI名は `EXPLANATION` |
| 説明ブロック | 説明コメントの対象となるID付きの一パーツ。描画表示の「ブロック」や「変更ブロック」とは別 |
| パーツ | `text` / `code` / `diagram` / `sequence` / `flow` の型付き表示内容。本文と返信・発言で共通 |
| 説明版 | サーバが説明全体の受理ごとに進める整数。未作成は0、最初の説明は1 |
| 差分表示版 | レビュー全体の差分メタデータを取り込んだ世代。review所属と世代を持つtokenで識別し、ファイル内容の固定を意味しない |
| サーバの現在差分表示版 | サーバが現在提供するメタデータの版。contextが返す版 |
| 画面のコード表示版 | その画面がapi/reviewを取り込み、Code用の一覧として保持している版。ほかの画面の取り込みでは変わらない |
| 説明の基点 | 説明作成に使った差分表示版のtoken。説明内容の正しさを保証しない |
| 説明の見方 | EXPLANATIONの画面。Code/Page、入力モード、表示モード、グループ単位とは別の軸 |

コメントはFile/Pageに加えて説明ブロックにも付けられる。
説明コメントの引用とoutdatedの読みは下の契約による。File/Pageの読みは現行のまま。

## R-EXPLANATION-VIEW 入口と移動

### 要件

- 上部の切り替えは `EXPLANATION` / `Code` / `Page`。Pageは従来の `--live` レビューでだけ使える。
  左側は順に説明の見出しリスト、従来のファイルツリー、従来のページのツリーとなる。
  Conversationは共通で、見方を変えてもスレッド、書きかけ、開閉を維持する。
- 開始時に説明があればEXPLANATIONを開く。なければ入力モードごとの従来の初期表示を使う。
  説明のない間はEXPLANATIONを押せない状態にし、まだ説明がないと示す。
- `Final state` / `Per commit` はCodeかつコミット範囲でだけ表示する。
  説明は両グループ単位を横断する。切り替えは説明版を変えない。
- 途中の説明追加・更新は知らせを出すだけで、現在の見方、開いた説明版、項目、読み位置を変えない。
  読んでいる説明版は、利用者が知らせから新版を開くまで維持する。
- ブロックの参照を押すとCodeまたは登録済みのlive Pageへ移る。
  Code参照はその画面のコード表示版の一覧で解決する。サーバの最新一覧へ自動更新してから移動しない。
  説明の基点と画面のコード表示版が違う場合は、その対応を示し、移動できても旧基点の内容を再現したとは示さない。
  戻る操作は元の説明版・項目・読み位置に戻す。更新が届いても元の読み場所を失わない。
  参照先が後の更新で消えた場合は利用不可の理由を示し、別の対象へ推測で移らない。
- 説明を読んだだけではファイルのSeenを付けない。承認の意味は [R-SUBMIT](output.md#r-submit-送信と契約) のまま。
  幅720px未満でも切り替え、目次、コメント、戻る操作を利用できる。既存の引き出し・シートの読みを使う。

### 成功条件

- 説明あり/なし、live/非live、コミット範囲/worktreeの組で初期表示と切り替えの有効状態を観測できる。
- 説明版1の中ほどからCode/Pageへ移り、版2の通知後に戻っても版1の同じ項目と読み位置を表示する。
- Codeを読んでいる間の途中追加が画面を奪わず、Seen数を変えない。390px幅でも同じ移動ができる。

### 反例

- 説明更新で先頭へ飛ぶ。EXPLANATIONにもPer commitを出して別の説明に切り替える。
- 図を読んだだけでCodeを閲覧済みにする。Page参照を任意URLへのアクセスに使う。

## R-EXPLANATION-READING 読む画面とコメントの入口

見た目の参照は [design/ui-mock-explanation-reading.html](../design/ui-mock-explanation-reading.html)。
モックの上部の帯と「決めたいこと」の枠はモック用で、画面には出さない。
モックの冒頭の大見出しと導入文は、実際には最初の節の内容として書かれる。説明のJSONに新しい欄を足さない。

### 要件

- 説明は節を畳まずに上から一続きの文書として表示する。節を箱や枠で囲わない。
  節の区切りは、番号付きの見出し、見出しの下の線、節の前の余白で示す。
- 左の目次は節の見出しを番号付きで並べ、textパーツ内のMarkdown見出しを一段下げて並べる。
  読み位置にある項目を示し、押すとその位置へ移る。幅はドラッグとキーボードで変えられる。
  各節のコメント数を目次の項目に出す。720px未満では目次を引き出しで開く。
- ブロックごとに常に出るコメントの操作を置かない。コメントの入口は次の二つだけとする。
  - text・codeパーツ：本文の文字を選ぶと、選んだ範囲の近くにコメントのボタンが出る。
    押すか、選択中に `c` を押すと入力欄を開く。選択が二つ以上のブロックにまたがるときはボタンを出さず、
    ブロックをまたいでコメントできない理由を同じ場所に出す。
  - 図（diagram・sequence・flow）：図の操作に置くコメントのボタンで、図全体を対象に入力欄を開く。
- 入力欄は選んだ範囲（図ではボタン）のすぐ下に浮かべて出す。選んだ文字を隠さず、本文と一緒にスクロールする。
  720px未満では本文の幅いっぱいに出す。入力欄には対象の節見出しと、選んだ文字（図では図の見出し）を引用として出す。
  Escで閉じる。書きかけの扱いは既存のコメント入力に従う。
- 保存したコメントは、選んだ文字に付箋色の印を付け、選択の終わりを含む段落・リスト項目・コードの直下に
  コード差分と同じ一行の札で出す。図へのコメントと、選んだ文字の位置を再現できないコメントは、
  ブロックの左に付箋色の線を付けてブロックの直下に札を出す。札を押すと会話パネルでそのスレッドを開く。
- 図の操作は縮小・拡大・全体表示・別表示・コメントに絞り、図の見出しの行の右に小さく置く。
  ポインタを図に乗せたときと図の中にフォーカスがあるときに出し、ホバーできない端末では常に出す。
  インラインのパンはドラッグと、図にフォーカスがある間の矢印キーで行う。別表示では従来どおりパンのボタンも出す。

### 成功条件

- 1280pxと390px、light・darkのそれぞれで、節に枠と開閉の操作がなく、目次の項目を押すとその節へ移る。
- 段落の途中の数文字を選んでコメントを保存すると、入力欄は選んだ行のすぐ下に出て、保存後はその文字に印が、
  その段落の直下に札が付く。二つのブロックにまたがる選択ではボタンが出ず理由が出る。
- 図のコメントのボタンをキーボードとタッチで押せ、入力欄の引用が図の見出しになる。
- インラインの図を矢印キーでパンでき、別表示を閉じると元の図へ戻る。

### 反例

- ブロックごとのアイコンや「Comment on this block」を常に出す。選んだ場所から離れた位置（ブロックの最後など）に入力欄を出す。
- 目次があるのに節を畳ませる。図の上にボタンを常に並べる。

## R-EXPLANATION-DOCUMENT 説明の構造

### 要件

- 説明は `sections` の配列で読む順を持つ。各節は `id`、plainな `title`、`blocks` を持つ。
  各ブロックは `id`、一つの `part`、`references` を持つ。複雑な入れ子ツリーは初版に含めない。
- 節IDは説明内で一意、ブロックIDは全節を通して説明内で一意。
  IDは作成者が維持し、サーバは位置や内容から付け替えない。
  段落を別々にコメントさせたいときは作成者が別のtextブロックに分ける。
  一つのMarkdownパーツ内の行やDOM要素へ自動で別IDを付けない。
- パーツは [共通パーツ](content-parts.md) の契約に従う。見出しはMarkdownとして解釈しない。
- `references` は0個以上。参照は表示内容とは別の型付きリンクで、任意URLや任意ファイルを開く機能ではない。
  以下の波括弧はJSON値ではなく型記法で、列挙したフィールドはすべて必須。
  Codeは `{type:"code",unit,group_id,path,side,start_line,end_line}`。
  `unit` はコミット範囲なら `file` / `commit`、それ以外はnull。
  `side` は `old` / `new`、全ファイル参照は行の両端がnull、行参照は両端が1以上で逆転しない整数。
  `group_id` と `path` は指定単位の一つのエントリを指す。移動時は画面の一覧で厳密に解決し、片側の有無と行範囲を確認する。
  行数未取得・内容読み込み対象外のエントリでは全ファイル参照のみを移動可能とし、行参照には理由を表示する。
  Pageは `{type:"page",url}`。`url` は既存liveのパスとクエリの読みで、登録済みページのみを指す。
  非liveのPage参照、未登録Page、未知の節/ブロック参照、参照の型や行範囲の形の不正は全体を拒否する。
- Code参照の投入時の扱いは説明の基点によって分ける。
  サーバの現在差分表示版を基点にした場合は、そのメタデータで対象・片側・行範囲を検証し、未知・曖昧・範囲外なら全体を拒否する。
  同一reviewの既知の旧基点は、過去の参照索引を持たなくても説明全体を受理する。
  旧基点のリンクは型と範囲の形だけを検証し、歴史的な対象の存在を確認したとは扱わない。
  画面の一覧で一意に解決できるリンクだけ移動できる。解決できないリンクは `Reference unavailable for this display version` と理由を示す。
  実際のCode移動では一覧のエントリから既存file_idを得る。入力のpathから任意のファイルを読む経路は作らない。
- 過去の全世代のCode参照索引を保存しない。現在メタデータと各画面が取り込んだ一覧を使う。
  参照検証のために全ファイルを新たに読むことはしない。Page参照は投入時点の登録ページ一覧で検証する。
  ページ登録が増えても差分表示版を進めず、contextのpagesには取得時点の登録一覧を返す。
  遅延読み込みのため行数と後で読む実内容が一致する保証はない。移動時にも現行の対象の存在を確認し、行を黙って縮めない。

### JSON値の例・提案

これは説明作成用の架空の値であり、現在のAPIや実ファイルの存在を表す例ではない。

```json
{
  "sections": [
    {
      "id": "overview",
      "title": "更新の入口",
      "blocks": [
        {
          "id": "update-intent",
          "part": {"type": "text", "body": "取り込み後も**読んでいる位置**を保つ。"},
          "references": []
        },
        {
          "id": "update-order",
          "part": {
            "type": "sequence",
            "title": "取り込み順の例",
            "role": "example",
            "participants": [{"id": "reader", "label": "Reader"}, {"id": "server", "label": "Server"}],
            "events": [{"type": "message", "from": "reader", "to": "server", "label": "Refresh", "kind": "call"}]
          },
          "references": []
        }
      ]
    }
  ]
}
```

### 成功条件

- text、コード、図を別IDで並べ、それぞれにコメントできる。一節と一つのtextだけの説明も受理する。
- 現在基点の未知パス、範囲の片端だけnull、未登録ページ、重複IDを含む説明は一つも反映しない。
- 既知の旧基点で過去索引のないCode参照を含む説明を受理し、表示中の一覧で解決できるものだけ移動できる。
  一覧にないpathは理由表示になり、ディスクへの任意読み取りを起こさない。

### 反例

- 目次の三章を必須にする。配列の添字をコメントのIDにする。参照先URLを勝手に登録する。

## R-EXPLANATION-COMMENT 対象と更新後の会話

### 要件

- 説明コメントは第三の対象で、`explanation_revision` と `block_id` を指定して作成する。
  サーバは保持中の説明版の存在とブロックを確認し、元の節見出しとブロック全体を引用の写しとして保存する。
  コメント本文は従来plainな `body` のまま。説明コメントにsuggestionやPageの案を付けない。
- 文字を選んで作るコメントは、任意の `selection` を添える。形は `{text,occurrence}` で、どちらも必須。
  `text` はブロックの表示上の文字列（描画したパーツの `textContent`）のうち選んだ範囲そのもので、1文字以上65,536バイト以下。
  `occurrence` は、その表示上の文字列の中で `text` が何番目に現れるか（0始まりの整数。一致は開始位置の早い順に数え、重なる一致も数える）。
  `selection` はtext・codeパーツのブロックにだけ付けられ、図のブロックでは拒否する。図や選択なしのコメントではnull。
  コメントの対象は `selection` があってもブロックのままで、ブロック全体の引用の写しも従来どおり保存する。
  サーバは形と上限だけを確かめ、表示上の文字列の中に `text` があるかは確かめない。表示上の文字列はブラウザの描画で決まるため。
  エージェントはブロック全体の引用を正とし、`selection` を利用者が指した箇所の手がかりとして読む。
- 画面は、outdatedでないコメントの `selection` を、現在の版の同じブロックの表示上の文字列の `occurrence` 番目の一致として印を付ける。
  一致が見つからなければブロック全体のコメントとして表示し、`selection` の値は変えない。
- 保存後は元の説明版、対象ID、引用の写し、`selection` を変更しない。
  図の短い表示がタイトルだけでも、スレッドから元のpart全体と参照を読める。
- 現在の説明に同じIDかつ同じ内容のブロックがあれば、元コメントを現在版のそのブロックにも表示する。
  ブロックの移動、節見出しだけの変更、ほかのブロックの変更ではoutdatedにしない。
  内容変更、削除、ID変更ではoutdatedとし、旧対象への会話として読む。
  後の版で同じID・同じ内容が戻ればoutdatedはfalseになる。元対象の写しは変わらない。
- 内容一致は `part` と `references` の型付き値を比較する。JSONの空白、キー順、文字エスケープの違いは無視する。
  配列順、すべての文字列、role、タイトル、座標、参照の変更は内容変更。
  CRLF/LF、末尾改行、空白、Unicodeの合成形、Markdownの等価な書き方を正規化しない。
  省略された任意フィールドと明示された既定値も別内容。nullは共通パーツの任意項目では不正。
  ハッシュだけの衝突で内容一致とせず、型付き値の一致を最終基準とする。
- Fileコメントは既存の正規化済み片側全体hashでoutdatedを判定し、Pageは従来false。
  これらと説明の一致規則を統合しない。承認対象の生バイト・identityには説明の比較を流用しない。
- 普通の質問にはスレッドへ追加説明を返す。本文の訂正や反映依頼には説明全体の更新を使える。
  ソフトは質問の意味から自動更新やコメント移動をしない。
  更新だけでスレッドを解決済みにせず、返事済みの行も消さない。解決は人だけ。

### 成功条件

- 版1の図へのコメントは、版2で別ブロックだけを変えても同じ図のそばに出る。
- 図のrole/座標、textの末尾改行、参照を一つ変えるとoutdatedになる。キー順だけならならない。
- 対象を削除・改名しても旧図の完全なJSONと会話を読め、元引用は保存時のままである。
- 同じ語が二回ある段落で二回目を選んで保存すると、`selection` の `occurrence` が1になり、再読み込み後も二回目に印が付く。
- 図のブロックに `selection` を付けたコメント、空の `text`、負の `occurrence` は保存されず理由が返る。

### 反例

- 似た段落にコメントを移す。図の引用からsource/events/nodesを捨てる。説明更新でresolveする。

## R-EXPLANATION-BASE 差分表示版と鮮度

### 要件

- レビュー全体に `diff_display_version` を導入する。値は `<review-id>:<generation>` の文字列で、認証用tokenとは別。
  generationは1始まりの連続する世代番号で、unsigned 128-bit整数を先頭ゼロのない10進文字列で表す。
  review-idの一致と発行済み最大世代以下であることを検証する。別review、0、未発行の未来世代、不正な形は拒否する。
  発行済み最大世代だけで既知判定し、全tokenや全参照索引を列挙して保存しない。
  初期の差分一覧を受理した時点で最初の値を発行する。
  利用者によるサーバ側の差分更新取り込みが成功したとき新しい値を発行する。失敗では進めない。
  取り込みが同じ一覧を返しても取り込んだ世代は進める。ソフトによる内容等価の推定はしない。
- テーマ、フォント、アニメーション、Page上の操作、描画の再計算、Code/Pageの切り替え、グループ単位切り替えで進めない。
  裏で他方のグループ単位の一覧を完成させる操作も同じ世代に属する。
- `api/review` の応答は、返したメタデータのtokenを持つ。各画面はその応答を自分のCode用一覧に取り込んだ時点でだけコード表示版を変える。
  サーバの現在差分表示版と画面のコード表示版は別の状態であり、複数画面で一致するとは限らない。
  説明のSSEは追加・更新の知らせと説明の基点を届けるだけで、Codeの一覧・コード表示版・cache・読み位置を更新しない。
  未取り込みの画面では説明の追加通知とCodeの更新バッジを区別する。
  contextはサーバの現在token・説明版・参照一覧を一回の整合した読みにして返す。各画面の表示版を返す要求ではない。
  二つの単位の一覧は混ざった世代で返さず、必要な一覧がまだ利用できなければcontextを理由つきで拒否する。
- 画面上の鮮度は、読んでいる説明の `base_display_version` とその画面のコード表示版を比較する。
  新しい説明の通知に示す鮮度は、その通知が指す説明の基点と同じ画面のコード表示版を比較する。
  旧説明を開いたままなら、その旧説明の鮮度と新版通知の鮮度を混同せず、読んでいる説明版は維持する。
  異なれば `Explanation for a different display version` と対応する二つの版を知らせる。
  Code用一覧をまだ取り込んでいない画面では判定を保留し、サーバ最新tokenをその画面の表示版と見なさない。
  同一reviewの既知の旧tokenは受理する。別reviewまたは未知tokenは拒否する。
  説明版番号、`file_id`、digest、既存の片側hashを代用しない。
- tokenはメタデータ取り込み世代の識別であり、全ファイルの固定、LLMが読んだバイトとの一致、説明の正しさの証明ではない。
  worktreeおよびファイル参照は表示時に読み直す。現行api/fileとブラウザcacheは現行内容版と結び付いていない。
  tokenが同じ間にも読まれる内容が変わりうる。tokenをapi/fileのバイト固定に使う改造は初版の範囲外。
  基点一致時に保証範囲の注意を常時表示しない。基点の情報詳細またはtooltipから、内容固定ではなく説明の正しさの証明でもないと読める。
  この情報入口は不一致の通知と区別し、描画条件の差を旧版として扱わない。

### 成功条件

- A/B画面がD1を表示中にAだけがD2を取り込み、D2基点の説明がBにも届く。
  contextはD2、D2説明の通知はAで基点一致、BではD1のままで不一致表示となり、BのCodeは自動更新されない。
  利用者がD2説明を開いても各画面で同じ判定となる。旧説明を読んでいた画面は、通知だけでは説明版を切り替えない。
  Bが自分でapi/reviewのD2を取り込んだときにだけBの鮮度表示が一致へ変わる。
- 旧tokenで説明を更新でき、別review/未知tokenでは説明も版番号も変わらない。
- フォント変更で図が描画失敗になっても基点tokenと鮮度判定は変わらない。
- 説明を使わず4096回を超えてCodeを更新しても、説明の容量やtoken件数を理由に更新を止めない。
- 基点一致時は常時注意文がなく、情報詳細から保証範囲を読める。不一致時には別の通知が出る。

### 反例

- digest一致をバイト一致の保証とする。ページのクリックごとに説明を古いとする。
- 旧tokenを受理するため全ファイル内容を固定して起動時に読み込む。
- Bの画面へD2の説明が届いただけでBのD1をD2と見なす。説明履歴の容量不足でCode更新を止める。

## 再利用の境界と調査根拠

shoryoの公開upstreamは [ba0918/shoryo](https://github.com/ba0918/shoryo)。調査元の `Cargo.toml` のrepository欄と `LICENSE` を照合した。
以下のshoryoのパスはこの公開リポジトリ内の相対パスで、特定のclone配置は実装の前提ではない。
調査時のcommitと公開upstreamの同一性は未確認。取り込み時に対象commitとライセンスを確認する。依存追加やコード取り込みの決定は今回行わない。

| 責務 | 再利用候補と境界 |
|---|---|
| 説明のID、版、参照、outdated | kemi側の純粋なドメイン。shoryoの質問・ラウンドモデルを持ち込まない |
| パーツ型と構造検証 | shoryoの `crates/shoryo-core/src/explanation.rs` と `crates/shoryo-core/src/explanation_validation.rs`。一つの検証契約を入出力・復元で使う候補 |
| Markdown | kemiの `crates/kemi-core/src/render/markdown.rs`、`inline.rs`、`url.rs`。パースと安全な描画は候補、差分整列と画像解決は説明に流用しない |
| sequence/flowの描画と幾何検証 | shoryoの `web/explanation-{sequence,flow,svg,bounds,layout-validation,collision}.js`。意味・版・コメントとは独立 |
| 図の操作 | shoryoの `web/components/explanation-{diagram,viewport,viewer}.js` と操作部品。kemiのviewsは通信せず、操作をactions経由でfeaturesへ渡す |
| grid図・コード | shoryoの `web/diagram.js`、`measure.js`、`web/components/code-part.js`。gridの省略とsequence/flowの無損失折り返しを混同しない |
| CLI・保存・会話 | kemiの `src/agent.rs`、`main.rs`、`crates/kemi-server/src/session.rs`、`api/agent.rs`、`api/submit.rs`、`web/assets/views/conversation.js` を拡張する境界 |
