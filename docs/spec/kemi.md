# kemi 仕様

- Status: 承認済み（2026-09-10）。UX 改訂 v2 承認済み（2026-09-11）。
  セッション改訂 承認済み（2026-09-18）
- 用語の定義: `CONTEXT.md`
- 改訂 v2 を一文で: 差分を「読む・変更間を移る・見終えたと分かる・結果を確実に受け取る」
  を速く確実にし、コミット範囲を最終形とコミットごとの両方で読めるようにする。
- セッション改訂を一文で: submit せずに終えたレビューを当時の差分ごとディスクに残し、
  あとから続きを読めるようにする。

結果を一文で: **kemi は、変更をブラウザで快適に読ませ、人間が付けた行コメントと
suggestion を実行ターミナルへ 1 つの JSON として返す、単一バイナリのローカルレビュー
道具である。**

各要件には「成功条件」（機械または人が観測できる確認）と「反例」（その要件が破られて
いると判定できる観測）を付ける。証拠の出所は `R-VERIFY` にまとめる。

## R-DIST 名称と配布

**要件**

- リポジトリ名とバイナリ名は `kemi`（「閲する」から）。
- ライセンスは MIT OR Apache-2.0。
- README と `skills/` の配布物は英語（翻訳版は作らない）、docs（この仕様を含む）は
  日本語。UI の文言（文章、ボタン、説明文、エラー表示、端末の選択画面）と CLI の出力
  （ヘルプ、エラーメッセージ、stderr の運用メッセージとライブ表示）は英語にする。エラーメッセージには
  kemi が作るすべてのエラー（入力の読み取り、manifest の検証、git の失敗、focus の
  検証、API のエラー）を含む。レビューの既定の `title`（`R-INPUT`）も英語にする。
- 対応ターゲットは次の 6 つ:
  - `x86_64-unknown-linux-musl` / `aarch64-unknown-linux-musl`（静的リンク）
  - `x86_64-apple-darwin` / `aarch64-apple-darwin`
  - `x86_64-pc-windows-msvc` / `aarch64-pc-windows-msvc`
- `aarch64-pc-windows-msvc` は CI の Windows ランナー上でのクロスコンパイルでビルドを
  検証し、ビルドできない場合は `x86_64-pc-windows-msvc` のみに落とす。
- GitHub Releases に cargo-dist 形式のアセットを添付する。unix は
  `<name>-<target>.tar.xz`、Windows は `<name>-<target>.zip` で、それぞれ
  checksum（`.sha256`）を付ける。`mise use -g github:ba0918/kemi` でインストール
  できる（動作確認は unix のみ。Windows での mise 経由は保証しない）。Windows の
  導入手順は zip を解いて `kemi.exe` を PATH へ置く。
- バージョンの正典はリポジトリ内の 1 箇所（ルート `Cargo.toml` の `version`）。
  タグは `v<semver>`。
- エージェント向けの使い方の文書を `skills/kemi/SKILL.md` に置き、リポジトリごと配る。
  形式は Agent Skills（agentskills.io の仕様。`SKILL.md` の先頭に `---` で囲んだ設定欄
  = frontmatter を持つ）。以下、この文書を「スキル」と呼ぶ。スキルは README と同じく
  この仕様から派生した配布物で、契約の正典ではない。正典はこの仕様で、スキルの文が
  契約を上書きしない。
  - 含むもの（括弧は書き写す元の節）: 起動と終了の待ち方 — レビュー中にタイムアウトで
    終了させない実行方法を選び、URL を伝えた後も終了コードと stdout の JSON を受け取る
    まで待機を継続する。ツールが処理を継続したまま一旦戻ることは、プロセスの終了ではない。
    ターンを終了してよいのは、終了通知でエージェントが自動再開されると確認できる場合だけ。
    それ以外は、実行識別子を保持し、待機・出力取得のツールを繰り返し使う。短い間隔での
    確認は避けるが、必要な待機は禁止しない。途中で止めない、会話の
    中の「承認」を verdict と見なさない（`R-SUBMIT`）。終了コードの表と、`130`
    （利用者による中止）では結果が無いが、保留ならセッションが残り、案内される
    `--resume` で続けられること（`R-SUBMIT`、`R-SESSION`）。入力モードの選び方と、
    `--group-by` の既定
    `file` とコミットごとを見せたいときの指定、`--no-open` / `--port` / `--bind` /
    `--focus`（`R-INPUT`）。manifest の書き方 — グループの `why` / `watch`、差分の `old` / `new` と
    `old_path` / `new_path`、`approval` の identity をエージェント自身が計算すること
    （`R-INPUT-1`）。結果 JSON の読み方 — 契約版 `kemi`、verdict、コメント、suggestion は
    エージェントが適用する、outdated の扱い、承認のときは identity を確かめてから進む
    （`R-SUBMIT`、`R-COMMENT`、`R-LIVE`）。`--result` での取り直し（`R-RESULT`）と、
    保留したレビューの再開（`R-SESSION`）。`--digest` の使い所（`R-DIGEST`）。
    起動後に人へ伝えること — URL、グループの数、
    最も見てほしい判断、自分の仮定（`R-VIEW`）。
  - 含まないもの: kemi の内部構造、ビルド、開発の手順。
  - スキルのディレクトリ内で自己完結する。`SKILL.md` は使用条件、起動から結果受け取り
    までの完了条件、必要な詳細への案内を持ち、入力形式や結果 JSON の詳細は同梱の
    `references/` に分けて必要なときだけ読む。他のスキルや外部の共有ファイルに依存せず、変更の提示の規範（例:
    差分を意図ごとにまとめる規則）は「あればそれに従う」と言及するだけ。本文（末尾の
    注を除く部分）は道具に依存しない言葉で書き、特定のエージェント向けの具体は末尾の注
    に分ける。
  - frontmatter は `name: kemi`、`description`（何をするか、いつ使うか）、`license` の
    3 つだけを持ち、ほかの項目は付けない。値は ASCII だけで書く（配布の道具の中に
    frontmatter を ASCII に限るものがある）。
  - 配布は、配布の定義ファイルを要らない経路（以下、コピー経路。symlink で置く道具を
    含む）だけ。保証するのは `gh skill install ba0918/kemi kemi`（GitHub CLI の組み込み。
    2 つ目の引数がスキル名）。`skills/kemi/` を手でコピーしても使える。README に載せる
    経路はこの `gh skill install` の 1 つだけ。`npx skills` と APM はこの形のリポジトリを
    読める仕組みだが未実測で、README には載せない。Claude Code / Codex の plugin の
    定義ファイル（`.claude-plugin/`）は置かない（`P12`、`R17`）。
  - スキルは frontmatter に版を持たない。届く内容は経路で決まる: `gh skill` はタグ付き
    リリースがあればその最新、無ければ既定ブランチの HEAD を配る。利用者に届けたい
    スキルの直しは、文面だけの変更でもリリース（`v<semver>` のタグ）で出す。ほかの経路
    の更新は、利用者が入れ直したときに届く。
  - CLI と JSON の契約を変えるコミットで、スキルと README も同時に直す。両者の一致を
    機械では検査しない（レビューで見る）。
  - README の `--bind` の説明に、公開が OS とネットワークに依存することを書く
    （OS のファイアウォール、WSL2 では Windows 側の設定、繰り返し公開するときの
    `--port` での固定）。kemi 自身はファイアウォールや転送の設定を行わない。

**成功条件**

- リリースタグのアセット一覧に、上の 6 ターゲットの成果物がある。unix は
  `kemi-<target>.tar.xz`、Windows は `kemi-<target>.zip` で、それぞれ対応する
  `.sha256` を付ける。
- きれいな環境で `mise use -g github:ba0918/kemi` の後、`kemi --version` が
  タグと一致するバージョンを出す（unix）。
- Windows の zip を解いた `kemi.exe` を PATH に置いた環境で、`kemi --version`
  がタグと一致するバージョンを出す。
- README と `skills/` 配下のすべてのファイルが英語で、docs が日本語、UI の文言と CLI の出力が
  英語である。
- e2e テストが、CLI のヘルプと、使い方の誤りで出力されるエラーメッセージに、日本語の
  文字が含まれないことを検証する。
- `skills/kemi/SKILL.md` の frontmatter が、`name` は親ディレクトリ名 `kemi` と一致、
  `description` は空でなく 1024 文字以内、項目は上の 3 つだけ、値は ASCII だけ、を
  満たす。`name` と `description` は Agent Skills の公式バリデータ
  `agentskills validate ./skills/kemi`（skills-ref。版の固定は `D3`）で、項目の数と
  ASCII は frontmatter を読む短い検査で確かめる。
- 最初のリリース以降、きれいな環境で `gh skill install ba0918/kemi kemi` の後、
  エージェントがスキルの手順だけで kemi を起動し、submit（承認または変更要求）まで
  到達して stdout の JSON を受け取れる（人による確認。エージェントはどれでもよい）。
- README に `--bind` の説明があり、OS のファイアウォール、WSL2 の Windows 側の
  設定、繰り返し公開するときの `--port` の固定に触れている。スキルにも `--bind` が
  ある（人による確認）。

**反例**

- スキルが、この仕様に無いフラグや JSON のキーを案内している。
- スキルの本文（末尾の注を除く部分）に、特定のエージェントの道具の名前が出ている。
- インストールされた `kemi` が動的ライブラリ不足で起動しない（musl 静的の失敗）。
- UI の文言（文章、ボタン、説明文、エラー表示）に、日本語の文言が残る。
- CLI の出力（ヘルプ、エラーメッセージ、stderr の運用メッセージとライブ表示）に日本語の
  文言が残る。

## R-INPUT 入力

入力は 4 つのモードのいずれか。同時に複数与えられた場合はエラー（終了コード 2）と
する。**グループの生成規則はモードごとに次のとおりで、`R-SUBMIT` / `R-DIGEST` /
`R-INPUT-5` はこの規則に従う。**

| モード | グループ | `id` | `title` |
|---|---|---|---|
| manifest | 作成者が決める | 作成者の値、省略時は `g1`, `g2`, … | 作成者の値（既定 空） |
| コミット範囲・コミットごと | マージ以外の各コミット | 完全な commit sha | commit の subject |
| コミット範囲・最終形 | 1 つだけ | `all` | `from...to` |
| worktree | 1 つだけ | `worktree` | "Working tree changes" |
| staged | 1 つだけ | `staged` | "Staged changes" |

コミット範囲は「最終形」と「コミットごと」の 2 つのグループ単位を両方持ち、画面で
切り替える（`R-UNIT`）。ほかのモードのグループ単位は 1 つだけ。

レビューの `title` は、manifest は `title` キー（省略時 "Review of changes"）、
コミット範囲は `from..to`、worktree は "Working tree changes"、staged は
"Staged changes" とする。

**成功条件**

- `kemi --worktree --staged` が終了コード 2 で終わる。
- `title` の無い manifest で、レビューの `title` が "Review of changes" になる。

**反例**

- 2 つの入力モードを同時に与えると、片方が黙って無視される。

### R-INPUT-1 manifest

既存 `diff-review` の manifest JSON と互換のキーをすべて受理する。入力は位置引数の
パス、または `-` で標準入力から読む。

| キー | 意味 |
|---|---|
| `title` / `subtitle` / `meta` | ページの見出し情報 |
| `groups[].id` / `.title` / `.why` / `.watch` | グループの識別子と理由、見てほしい点 |
| `groups[].diffs[].path` | 表示パス |
| `groups[].diffs[].old` / `.new` | 差分の左右を直接与える文字列 |
| `groups[].diffs[].old_path` / `.new_path` | 差分の左右をファイルから読む（`--base` 相対） |
| `groups[].diffs[].status` | `add` / `delete` / `rename` / `modify`（省略時は推論） |
| `groups[].diffs[].renamed_from` | 改名元。`status` 省略時は rename と推論 |
| `groups[].diffs[].focus` / `.note` | ファイル単位の重要と理由（`R-FOCUS`） |
| `approval[]` | 承認対象の `path` と `identity`（例 `sha256:...`） |

- 片側が無いことは追加・削除を意味する（空ファイルではなく、行が無いこと）。
- 同じ側に `old` と `old_path`（`new` と `new_path`）を同時に指定した場合は
  エラー（終了コード 2）。存在しないパスを指した場合もエラー（終了コード 2）。
  旧ツールはどちらも黙って空として扱ったが、kemi は黙って進まない。
- `id` 省略時は `g1`, `g2`, … を生成する（旧ツールと同じ形）。
- 各ファイルの統計（増減数）は起動時に求める（manifest では整列して求める）。
  行データの計算は `R-SERVE` に従い、表示された時に初めて行う。manifest は
  人が手で書く入力を想定し、起動時間の目標は設けない。巨大な入力を機械的に
  作りたい場合はコミット範囲モードを使う。

**成功条件**

- リポジトリ内の `tests/fixtures/legacy-manifest.json` を渡すと、レビュー API の
  メタデータが `tests/fixtures/legacy-manifest.expected.json`（グループ、パス、
  状態、増減数）と一致する。
- `kemi -` が標準入力の manifest を読む。

**反例**

- `old` と `old_path` が同時にあり、どちらが優先されるか決まっていない。
- 存在しない `old_path` が黙って空ファイルとして扱われる。
- 同じ manifest で起動するたびにグループ id が変わる。

### R-INPUT-2 コミット範囲

`--from <ref> [--to <ref>]`（`--to` の既定は `HEAD`）でコミット範囲を渡す。
コミット範囲は次の 2 つのグループ単位を持ち、1 回の起動の中で切り替えられる
（`R-UNIT`）。`--group-by` は起動時に表示する単位を選ぶ（既定 `file`）。

- 最終形（`--group-by file`、既定）: `--from...--to`（merge-base から `--to`）の
  全体を 1 つの差分としてファイルごとに 1 回だけ表示する。変更ブロックごとに
  由来のコミットを示す（`R-ORIGIN`）。
- コミットごと（`--group-by commit`）: `--from..--to` の各コミットが 1 グループ。
  グループの `title` は subject、`why` は body。**マージコミットはグループにしない**
  （変更一覧が空になり、レビュー単位として意味を持たないため）。
- 2 点ドットと 3 点ドットの非対称は意図: コミットごとは「各コミットが何を変えたか」、
  最終形は「ブランチ全体の最終形」を見るため。範囲にマージがある場合、マージ自体
  （衝突の解決）が変えた行は最終形にだけ現れ、コミットごとのどのグループにも
  属さない。
- 統計は `git diff --numstat` 相当で起動時に求める。行データは表示時に求める。
- ファイルの左右の内容は git オブジェクトから読む。改名は git の改名検出に従う。

**成功条件**

- 10,000 ファイルのフィクスチャ（`R-VERIFY`）で、コミットごとのグループ数が
  マージ以外のコミット数と一致する。
- 最終形では同じパスが複数グループに現れない。
- マージコミットのグループが存在しない。
- `--group-by` を付けない `--from` が最終形で始まる。

**反例**

- 最終形でコミットをまたいだ同じパスが複数グループに現れる。
- マージコミットが空のグループとして並ぶ。
- `--group-by` を付けない `--from` がコミットごとで始まる。

### R-INPUT-3 未コミット（worktree）

`--worktree` は `HEAD` と作業ツリーの差を表示する（ステージ済みと未ステージの
両方を含む）。untracked ファイルは「新規」として含める。

- 統計は `git diff --numstat HEAD` と untracked の行数から求める。行データは
  表示時に求める。
- サイズまたは種別の上限を超える untracked は、内容を出さず「バイナリ/巨大
  ファイル」として統計だけ表示する。上限値は D6。
- 監視の対象は作業ツリーのファイルそのもの（`R-LIVE`）。

**成功条件**

- untracked の新規ファイルが `add` として現れる。
- 上限を超える untracked が内容なしで一覧に出る。

**反例**

- untracked が無視され、レビュー対象から漏れる。

### R-INPUT-4 ステージ済み（staged）

`--staged` は `HEAD` とインデックスの差を表示する。作業ツリーの変更は含めない。
統計は `git diff --numstat --cached` 相当で求める。

**成功条件**

- 同じファイルにステージ済みと未ステージの変更があるとき、`--staged` は
  インデックス側の内容だけを表示する。

**反例**

- 未ステージの内容が混ざる。

### R-INPUT-5 focus レイヤ

`--focus <path>` は JSON ファイルを読み、入力モードに関係なくグループとファイルへ
focus と note を後付けする。パスは `--base` 相対。

```json
{
  "groups": { "<group-id>": { "watch": "…" } },
  "files": [
    { "path": "src/a.rs", "focus": true, "note": "ここが決定点" }
  ]
}
```

- `groups` のキーは `R-INPUT` の表で定義した `id`（コミットでは完全な sha）。
  許可するキーは `watch` のみ。それ以外のキーはエラー（終了コード 2）。
  コミット範囲では、起動時に最終形の `all` と範囲内のコミットの sha の両方と照合する
  （コミットごとの単位を作り終えるのを待たない）。
- `files` はパスで一致する。同じパスが複数グループに現れる場合はすべてに適用する。
  コミット範囲では両方のグループ単位に適用する。パスの照合も起動時に行い、最終形か
  範囲内のどれかのコミットに現れるパスを「存在する」とみなす（コミットごとのパスの
  一覧は、`--focus` を付けたときだけ起動時に求める）。
- 存在しない `group-id` や `path` を指した場合はエラー（終了コード 2）。
  黙って無視しない。
- manifest 側にも同じ項目がある場合、`--focus` の値が勝つ。
- focus の表示は `R-FOCUS`、`--digest` への反映は `R-DIGEST`。

**成功条件**

- 存在しないパスを書いた `--focus` が、そのパスを名指しして終了コード 2 で失敗する。
- 同じグループに `watch` が両方にある場合、`--focus` の文言が表示される。

**反例**

- タイポしたパスが黙って無視され、重要が表示されないままレビューが始まる。

### R-INPUT-6 その他の入出力

| フラグ | 意味 |
|---|---|
| `--base <dir>` | manifest と `--focus` の相対パス解決の基準（既定 `.`） |
| `--port <n>` | 待ち受けポート（既定 0 = 空きを選ぶ） |
| `--bind <addr>` | 待ち受ける IPv4 アドレス（既定 `127.0.0.1`。`0.0.0.0` は全 IPv4 インターフェース） |
| `--no-open` | ブラウザを自動で開かない |
| `--digest` | ページを出さず `R-DIGEST` の JSON を stdout に出して終了 |
| `--digest-top <n>` | digest のトップファイル数（既定 100） |
| `--serve` | 互換のための受理のみ（既定で常にサーブする） |
| `--out` | 廃止。静的書き出しはしない（`P10`）。指定されたら理由を出して終了コード 2 |
| `--group-by <commit\|file>` | コミット範囲で起動時に表示するグループ単位（既定 `file`、`R-UNIT`） |
| `--result` | レビューを始めず、結果ファイルの最新の結果を stdout に出して終了（`R-RESULT`） |
| `--any` | `--result` と一緒に使う。場所に関係なく最新の結果を選ぶ |
| `--workspace <path>` | `--result` と一緒に使う。結果を探す場所を起動ディレクトリの代わりに指定する |
| `--resume [<id>]` | 保留したセッションを復元する。`id` を省略すると対話で選ぶ（`R-SESSION`） |

- manifest を省略した場合、`--from` / `--worktree` / `--staged` / `--result` /
  `--resume` のいずれかが必要。
- どれも無い場合は使い方を stderr に出して終了コード 2。
- `--result` と一緒に使えるのは `--any` と `--workspace` だけで、それ以外のフラグや
  入力モード（manifest / `--from` / `--worktree` / `--staged` / `--resume`）との同時指定、
  `--result` なしの `--any` / `--workspace`、`--any` と `--workspace` の同時指定、
  `--from` なしの `--group-by` は、使い方の誤りとして終了コード 2。
- `--resume` と一緒に使えるのは `--port` / `--bind` / `--no-open` / `--serve` だけで、
  入力モード（manifest / `--from` / `--worktree` / `--staged`）と `--digest` /
  `--group-by` / `--base` / `--focus` / `--result` / `--any` / `--workspace` との
  同時指定は、使い方の誤りとして終了コード 2。
- `--bind` の値は IPv4 アドレスのリテラルだけを受理する。ホスト名と IPv6 は
  使い方の誤りとして終了コード 2。`--digest` はサーブしないため値を使わないが、
  検査はサーブ時と同じに行う。
- サーブ開始時に stderr へ `kemi: <url>` の 1 行を出す。この行は計測の
  インターフェースとして契約とする（`R-VERIFY`）。

**成功条件**

- `kemi --out x.html` が、静的書き出しが無いことを説明して終了コード 2 で終わる。
- サーブ開始後、stderr の 1 行から URL を取り出せる。
- `kemi --result --from HEAD~1`、`kemi --result --port 0`、`kemi --any`、
  `kemi --result --any --workspace .`、`kemi --worktree --group-by commit` が
  それぞれ終了コード 2 で終わる。
- `kemi --worktree --resume`、`kemi --resume --digest`、`kemi --resume --workspace .`
  がそれぞれ終了コード 2 で終わる。
- `kemi --worktree --bind localhost`（ホスト名）、`kemi --worktree --bind ::1`
  （IPv6）、`kemi --result --bind 0.0.0.0`（`--result` との排他）が、それぞれ
  終了コード 2 で終わる。

**反例**

- `--out` が黙って無視され、ファイルが出ないまま成功扱いになる。
- `--result` なしの `--any` が黙って無視され、レビューが始まる。
- `--resume` に元のモードのフラグを足すと、黙って無視されてセッションと違うレビューが始まる。
- URL の行が stdout に出て、submit の JSON と混ざる。
- `--bind` の値が検査されず、意図しないアドレスで待ち受ける。

## R-SERVE 配信モデル

**要件**

- 常に HTTP サーバを立てる。既定では `127.0.0.1` にだけバインドし、他端末から
  到達できない。静的 HTML は書き出さない。
- 起動時に計算するのは、起動時に表示するグループ単位のファイル一覧・状態・統計・
  グループ情報まで。コミット範囲のもう片方のグループ単位は、`api/review` の最初の
  応答を返した後に裏で作る（`R-UNIT`）。行データと由来（`R-ORIGIN`）と描画（`R-RENDER`）は
  ファイルが表示された時に初めて計算して配信する。ただし行データは、`n` / `p` の
  移り先を決めるために、そのファイルに止まる場所があるかを確かめる時にも計算して
  よい（`R-NAV`）。
- バインド先は `--bind <IPv4>` で変えられる（既定 `127.0.0.1`、`0.0.0.0` は全
  IPv4 インターフェース）。ループバックは `127.0.0.0/8` とする。
- URL は `http://<host>:<port>/s/<token>/` の形。`token` はセッションごとの
  ランダム値で、URL を知らないページからの API 利用を防ぐ。`<host>`（以下、
  共有アドレス）は、具体アドレスへのバインドならそのアドレス、`0.0.0.0` なら
  既定経路のローカルアドレス（std の UDP connect で得る。パケットは送らない）
  にする。`0.0.0.0` で特定できないときは `127.0.0.1` のままとする。既定経路が
  VPN などのときは LAN のアドレスにならないことがあり、そのときは
  `--bind <自分のIP>` で指定する。
- 共有アドレスの取得は、特定できない場合も含めてテストから差し替えられる形に
  する（差し替えの形は実装が決める）。取得と `Host` の検証に新しい依存は
  足さない。
- 非ループバックで待つときは、URL の行の後に警告を 1 行出す。警告は英語で、常に
  `kemi: exposed on the LAN;` で始める。共有アドレスを特定できたときは、続けて
  URL を知る人は誰でも閲覧と submit ができ、平文 HTTP であることを述べる固定の
  1 文にする:
  `kemi: exposed on the LAN; anyone with the URL can read the diff and submit over plain HTTP.`
  特定できないときは、続けて取得できなかったことと `--bind <自分のIP>` で明示
  できることを述べる（文面は実装が決める）。どちらの場合も、公開のリスク
  （誰でも閲覧と submit ができること、平文 HTTP）を述べる。
- ブラウザを自動で開くときは URL を開く（`0.0.0.0` のときは `127.0.0.1` に
  読み替える）。
- 公開が他端末から実際に届くかは OS とネットワークに依存し、kemi は関与しない
  （ファイアウォールや転送の設定を行わない）。
- API は同じオリジンのページからの呼び出しだけを受理する（`Origin` と `Host` を
  検証する）。クロスオリジンの `POST` は拒否する。`POST` の `Host` は port が
  待ち受け port と一致し、ホスト部が `127.0.0.0/8`・バインドした具体アドレス・
  共有アドレスのいずれかであるときだけ受理し、`Origin` は `http://` + 受理した
  `Host` と完全一致することを要する。許可をこの 3 つに限るのは、公開の範囲を
  広げず DNS rebinding を防ぐため。共有アドレス以外のローカルアドレス経由で
  開かれたページの `POST` は 403 になる（利用者には URL を案内するため通常は
  起きない。別のアドレスで使いたいときは `--bind <そのアドレス>` で起動する）。
- API の契約（最低限の一覧。由来やもう片方のグループ単位を届けるためなどの
  エンドポイントの追加は D7）:
  - `GET /s/<token>/api/review`: グループとファイルのメタデータ。各ファイルは
    不透明な `id` を含む。
  - `GET /s/<token>/api/file/<id>`: そのファイルの整列済み行データ。
  - `POST /s/<token>/api/comment`: コメントの追加・編集・削除・返信・解決（`R-COMMENT`）。
  - `POST /s/<token>/api/submit`: submit（`R-SUBMIT`）。
  - `GET /s/<token>/api/events`: `R-LIVE` の通知（SSE）。
  - `GET /s/<token>/api/image/...`: 画像のバイト列（`R-RENDER`）。2 種類あり、どちらも
    `GET` だけで、URL の形は D7。
    - レビュー対象の画像の旧・新: kemi がそのレビューで読んだバイト列をそのまま配る
      （入力モードを問わない。復元では写しから）。
    - Markdown の相対パス画像: リポジトリの中に正規化できるパス（symlink は辿らず、
      symlink そのものは配らない）で、`R-RENDER` の画像形式で、上限以下のものだけ。
      manifest と復元では配らない（`R-RENDER` の表）。
    - どちらも条件を満たさないものは 404。応答には、拡張子から決めた `Content-Type` と
      `X-Content-Type-Options: nosniff`、`Content-Security-Policy: sandbox` を付ける。
      同じオリジンで直接開かれた SVG の中のスクリプトが kemi の API に届かないため
      （sandbox の文書は別オリジン扱いになる）。
- 内部 API の JSON 形（行データのフィールド名など）は実装が決める（D7）。
- 複数の端末から見られていても、セッションは 1 つで、利用者は区別しない。コメントに
  著者は付かない（利用者の認証を作らない。P5）。submit の受理は 1 回だけの既存の
  契約のまま（`R-SUBMIT`）。
- セッション状態（コメント、見た、折りたたみ、解決）はサーバのメモリに置き、
  変更のたびにセッションファイルへも書く（`R-SESSION`）。プロセス終了で失われるのは
  写しの作成が終わる前の内容だけ。submit を確定した結果の JSON は結果ファイルに
  残す（`R-RESULT`）。ブラウザの localStorage は表示の好み（表示モード・テーマ）と
  下書きにのみ使う。

**成功条件**

- 10,000 ファイルのフィクスチャで、プロセス開始から `api/review` の初回応答までが
  1 秒未満（release ビルド、`scripts/measure-startup.sh`、3 回の中央値）。
  この条件は起動時に作るグループ単位に適用する。
- 起動と `api/review` はファイル内容を読まない（テストで、内容取得の呼び出し
  回数が 0 であることを確認する）。行データは `api/file` の応答に必要な時に
  初めて計算する。
- URL の token 無しの API 呼び出しが 404 または 403 で拒否される。
- `Origin` の異なる `POST` が拒否される。
- `kemi --bind 0.0.0.0 --port 0 --no-open` の stderr から URL を取り出し、その URL の
  `api/review` が応答する。URL の行の後に `kemi: exposed on the LAN;` で始まる警告行が
  ある。
- 既定で起動したとき、URL が `http://127.0.0.1:<port>/s/<token>/` の形で、警告行が
  無い。
- 共有アドレスの取得をテストから差し替えてアドレス A を返させたとき、URL の host が
  A になり、警告が固定の 1 文になる。`Host: A:<port>` と対応する `Origin` の `POST`
  が受理され、他のアドレスを `Host` に持つ `POST` は 403 になる。
- 共有アドレスを特定できないように差し替えたとき、URL が
  `http://127.0.0.1:<port>/s/<token>/` になり、警告が `kemi: exposed on the LAN;` で
  始まり `--bind` を含み、LAN 側のアドレスを `Host` に持つ `POST` が 403 になる。
- `--bind 0.0.0.0` でブラウザを自動で開くとき、開かれる URL が `127.0.0.1` である
  （人による確認）。
- 2 つのクライアントで同じ URL を使い、片方で付けたコメントと見たがもう片方から
  見える。submit の JSON に著者のフィールドが無い。

**反例**

- 起動時に全ファイルの内容を読んで行データを作る（10,000 ファイルで 1 秒を超える）。
- 最終形で起動したのに、コミットごとの単位を作り終えるまで `api/review` が返らない。
- `--bind` 無しで `127.0.0.1` 以外にバインドされ、他端末から到達できる。
- 非ループバックで待つのに警告が出ない。または警告が公開のリスクを述べない。
- `0.0.0.0` のとき任意の `Host` を受理し、別オリジンのページから `POST` が届く。
- 許可の範囲が URL とバインドで決まらず、実行環境のインターフェース一覧に広がる。
- URL の token 無しで API が応答する。
- 別オリジンのページからの `POST` が受理される。

## R-VIEW 差分の表示

見た目は diffs.com（OSS ライブラリ `@pierre/diffs`、Apache-2.0）を参照するが、
コードはコピーしない。

**要件**

- 1 列（unified）と 2 列（split）を切り替えられる。行番号、変更記号、単語単位の
  強調、ハンクの折りたたみと展開（クリックでその場に開く）を持つ。
- 1 列表示では、連続する書き換えを「消した行の塊 → 足した行の塊」の順に並べる。
  旧と新を 1 行ずつ交互に並べない。単語単位の強調は、対応する旧と新の行の組で保つ。
- 2 列表示では、書き換え行の旧側を削除の色、新側を追加の色で塗り、変更箇所の強調も
  旧側は削除の強調色、新側は追加の強調色にする。相手の無い側（追加だけ・削除だけの
  行の空いた側）は追加・削除の色を付けず、斜線の無地にする。
- 行番号の欄にも、その行の追加・削除の色を付け、変更記号（`+` / `−`）を太くする。
- 折りたたみ行には、隠れている行数を示す展開の操作と、その下に続く表示範囲の旧・新の
  行番号（git の `@@` と同じ意味）を出す。囲みの文脈（関数名など）は出さない
  （`P11`）。
- 最終形では、各変更ブロックのすぐ上に 1 行の「由来の行」を出す（1 列でも 2 列でも）。
  中身は `R-ORIGIN` の由来。由来を計算している間は行だけ先に出して計算中の印を置き、
  後から行が増えて表示がずれないようにする。由来が既定で無効のファイル（`R-ORIGIN`
  の上限を超えるもの）では由来の行を出さず、有効にすると出す。最終形以外では出さない。
- ファイルヘッダは追従（sticky）し、左のファイルツリーから各ファイルへ飛べる。
  狭い画面（`R-NARROW`）ではツリーは引き出しになる。
- ファイルを選ぶと、ファイルヘッダは内容の取得を待たずに選んだファイルへ切り替わる。
  取得が終わるまで、ヘッダの操作（見た・コメント・展開・ハイライト・描画表示の切り替え）は無効にする。
- 構文ハイライトをサーバ側で行う。左右それぞれのファイル内容を行単位で着色し、
  複数行にまたがる文字列・コメントを壊さない。
- 1 ファイルの片側が 10,000 行超または 1 MB 超のときはハイライトを切って表示し、
  そのファイルでだけ有効化できる。
- 折返しは既定で無効（横スクロール。狭い画面は `R-NARROW`）。有効にした場合も行の高さを実測して
  描画を破綻させない。2 列表示の横操作は `R-VIEW-HSCROLL` に従う。
- 表示する行を作り直す操作（折りたたみの展開と畳み直し、表示モードと折返しの
  切り替え、由来の出し入れ、テーマとハイライトの変更）でも、上端に見えていた行はその
  位置に残す。取得した行をそのまま並べ直す作り直し（折りたたみの展開と畳み直し、
  表示モードの切り替え、由来の出し入れ）では、同じファイルで測った行の高さを引き継ぐ。
  折返しの切り替えと、行を取り直すテーマやハイライトの変更では、高さを測り直す。
- 表示中の行だけを DOM に載せる。1 ファイル 50 万行でもスクロールが固まらない。
  行要素は `data-kemi-row` 属性を持ち、自動検査が数えられる。描画表示（`R-RENDER`）は
  行を持たず、上限の範囲で文書全体を載せる。
- ノイズ（`CONTEXT.md` 参照）に分類したファイルは既定で畳んで表示し、開ける。
  分類は 1 つの分類器で行い、規則（パスパターン、`.gitattributes` の
  `linguist-generated`、バイナリ判定）は実装に委譲する（D6）。
- 増減数で並べ替えるトグルを持つ。既定の並びは入力の順で、トグルを操作した時だけ
  並びが変わる。入力の順は、manifest は配列の順、コミットごとはコミットの古い順、
  最終形・worktree・staged のファイルは git の差分の出力順（パスの順）。
- ページ上部に `title` / `subtitle` / `meta` を表示し、表示モード・折返し・
  重要のみ・変更量順・テーマの操作を、文字ラベルを出さないモノクロのアイコンと
  ツールチップでまとめる。例外として、コミット範囲ではグループ単位の切り替えを
  "Final state | Per commit" の文字付き 2 択でタイトルの右に置く（`R-UNIT`）。
  上部にはほかに、見たの進捗（`R-SEEN`）、コメント件数付きのコメント一覧の入口、
  更新バッジ（`R-LIVE`）、承認と変更要求のボタン（`R-SUBMIT`）を置く。左上の名前は
  `kemi` の文字にする。
- 本文側のグループ帯（表示中のファイルが属するグループの見出し）には `title` を
  表示する。`why`（説明）は既定で畳み、開ける。開閉の状態はページを開いている間
  だけ覚える。`watch`（見てほしい点）は畳まずに常に表示する。ツリーのグループ
  見出しには `title`、見たの進捗（`R-SEEN`）を出し、`why` と `watch` は出さない。
- コミットごとの単位で、件名が「英小文字の種類、続いて任意の `(scope)`、任意の `!`、
  最後に `:` と空白」で始まるとき（例 `feat: `、`fix(ui)!: `）、`:` の前までを色の無い
  小さな枠で示し、件名からは外す。対象はツリーのグループ見出しと本文側のグループ帯
  だけで、コメント一覧と由来は件名をそのまま出す。submit JSON の `group_title` は
  件名のまま変えない。
- ファイルヘッダに、パスのコピーと全行展開の操作と、そのファイルのコメント件数
  （ファイル全体へのコメントを含む）を持つ。Markdown と表と SVG のファイル（`R-RENDER`）では、
  描画表示とソース表示の切り替えも持つ（SVG 以外の画像は持たない）。
- コメントの入口は行にホバーすると出る `+` とし、行番号のドラッグでレンジを
  選べる（狭い画面では `R-NARROW` のタップ）。ファイル全体へのコメントはファイルヘッダから入れる。suggestion は
  コメント入力の一部として置換後のテキストを書き、コメントに添えて表示する。
  適用はエージェントが行うことを画面に示す。常設のコメントパネルは持たない。
- 行コメントは、対象範囲の最後の行の直下に、コードの列の位置から始まる吹き出しで
  表示する。吹き出しは対象の行を指し、範囲の行には行番号の欄の左端にコメントの色の
  線を付ける。
  コメントは既定で本文の 1 行目を見せる 1 行の札に畳み、押すと開いて本文を
  すべて見せる。付けた直後のコメントは開いた状態で出し、別のファイルへ移って戻っても、
  ページを開いている間は開いたままにする（押して畳んだものは畳んだまま）。開閉の状態は
  ページを開いている間だけ覚える。吹き出しの本文の表示幅は約 72 文字に制限し、超える行は
  折り返す（入力の文字数は制限しない）。札の 1 行目が収まらないときは省略記号で
  切る。作成者の札
  （「あなた」）は出さない。ファイル全体へのコメントはファイルヘッダの下に同じ
  吹き出しで出す。
- 上部のコメント一覧の入口を押すと、すべてのグループ単位のコメントを並べた一覧が
  開く。各項目はグループ単位、パス、行範囲、本文の 1 行目を示し（コミットごとの
  項目はそのコミットの件名も示す）、押すとその単位へ切り替えてその行へ移る。
  履歴の書き換えで消えたグループのコメント（`R-LIVE`）は「消えたコミット」として
  示し、押しても移らず本文を見せるだけにする。一覧は閉じると消える（常設パネルでは
  ない）。
- 左のツリーはグループとディレクトリを開閉でき、ファイルとディレクトリを
  テーマ色に追従するモノクロの SVG アイコンで区別する。
- ファイルツリーにはパス、状態、増減数、ノイズかどうか、重要かどうか、コメントの
  件数、見たかどうか（`R-SEEN`）を示す。状態は 1 文字（`A` 追加 / `D` 削除 /
  `R` 改名 / `M` 変更）で示し、`M` は目立たせない。
- 本文の基準サイズは 15.5px とし、余白もそれに比例させる。
- 配色は意味ごとの役割に分ける: 進捗・見た・主な操作は藍系、コメントは付箋の黄系、
  重要と見てほしい点は藤（紫）系、追加は緑系、削除は赤系。追加と削除以外の役割に
  赤系の色を使わない。各テーマでの具体的な色の値は D2。
- 見た目の参照は `docs/design/ui-mock-v2.html`（採用したモック）に置く。モックと
  この仕様が食い違うときは仕様が正しい。
- テーマは light / dark の自動と手動切替、および数種のプリセットを持つ。
  配色は CSS 変数に閉じる。
- バイナリは内容を出さず、バイト数の増減だけを示す。例外は `R-RENDER` の画像で、
  上限の範囲で旧と新の画像を並べる。
- CRLF と LF の違いは表示時に正規化し、改行コードの変更のみを差分として
  強調しない。最終行の改行の有無は表示しない。
- `approval` は画面に出さない。`identity`（承認対象を識別する値。manifest が与える）は
  人が照合できる値ではなく、エージェントが承認後にコミットするバイト列と突き合わせる
  ための記録なので、結果の JSON にそのまま返すだけにする（`R-RESULT`）。

**成功条件**

- 50 万行のフィクスチャファイルを開いてスクロールしても操作が固まらない
  （人が確認）。併せて、DOM 上の `data-kemi-row` 要素数が表示中の行数程度に
  収まる（ブラウザ自動化で確認）。
- 10,000 行超のファイルでハイライトが切れ、当該ファイルで有効化できる。
- `Cargo.lock` などの lockfile が既定で畳まれ、開ける。
- 広い画面（`R-NARROW`）で、ヘッダに `subtitle` と `meta` が出る。
- グループ見出しに `watch` が常に出て、`why` は畳まれた状態から開ける。
- 1 列表示で、連続する 3 行の書き換えが旧 3 行、新 3 行の順に並ぶ（表示行を作る
  純粋関数のテスト）。
- 測った行の高さと上端の行を、作り直しの前後で対応づける純粋関数のテストで、
  上に隠れた開いたコメントの高さが折りたたみの展開後も残り、消えた行の高さは残らず、
  上端の行が展開や由来の追加の後も見つかる。画面では、上に隠れた開いたコメントが
  ある状態で下の折りたたみを展開しても、上端に見えている行が変わらない（人が確認）。
- 2 列表示で、書き換え行の旧側に削除の色、新側に追加の色が付き、相手の無い側に
  追加・削除の色が付かない（人が確認）。
- ファイルを切り替えた直後、取得が終わる前に見たを押しても、前のファイルに
  見たが付かない（ブラウザ自動化で確認）。
- 複数行のコメントが範囲の最後の行の直下に出る（配置を決める純粋関数のテスト）。
- 既存のコメントが 1 行の札で出て、押すと本文がすべて見える（人が確認）。
- コメント一覧から選んだコメントの行へ、グループ単位をまたいで移れる（人が確認）。
- ツリーのグループとディレクトリが開閉できる。
- ファイルヘッダのパスコピーと全行展開が動く。
- 行の `+` からコメントを追加でき、その行の直下に表示される。
- 常設のコメントパネルが存在しない。広い画面（`R-NARROW`）で、上部バーの表示の操作
  （表示モード・折返し・重要のみ・変更量順・テーマ）は文字ラベルを持たない。文字ラベルを持つ上部バーの
  操作は、グループ単位の切り替え、送信のボタン、更新バッジ、コメント件数付きの
  コメント一覧の入口だけである（title / subtitle / meta、`kemi` の名前、見たの
  進捗は操作ではないので、この条件の対象外）。
- 「見た」と折りたたみの状態が再読込後も残る。コメントはセッションが残る限り残り、
  保留と復元をまたいで続く（`R-SESSION`）。

**反例**

- 50 万行すべてを行要素として生成する。
- ハイライトが 1 ファイルの全行を起動時に処理する。
- 改行コードだけの変更が、全行の変更として表示される。
- lockfile が通常ファイルとして展開される。
- ノイズ判定が 2 箇所にあり、ツリーと本文で結果が食い違う。
- コメントが常設パネルにしか出ない。
- 送信の確認をキャンセルしてもレビューが終了する。
- 1 列表示で、書き換えの旧と新が 1 行ずつ交互に並ぶ。
- 2 列表示で、書き換え行に色が付かない、または旧側の変更箇所が追加の色になる。
- 取得中にヘッダの見たを押すと、前に表示していたファイルに見たが付く。
- 範囲コメントが範囲の途中に割り込み、範囲の行が上下に分かれる。

### R-VIEW-HSCROLL 2 列表示の同期横スクロール

長い行の続きがあると分かり、折り返さずに旧・新の同じ横位置を比較できるようにする。
対象は 2 列表示のみ。1 列表示は既存の横スクロールを維持する。

**要件**

- 折返しが無効で、実測済みのコードに表示幅を超えるものがある場合、差分表示領域の
  下端に横スクロールバーを 1 本設ける。ファイルの末尾まで縦に移動しなくても操作できる。
  行ごと・左右別々のスクロールバーは設けない。
- バーの操作で、表示中の全行の旧・新のコードを同じ画素数だけ横に動かす。
  短い行や相手の無い側も同じ横位置を使い、コードが尽きた部分は空白とする。
  コードは各ペイン内に収め、隣のペインに重ねない。
- 行番号、変更記号、中央の境界、コメントと入力欄、由来の行と理由、折りたたみの
  操作は横に動かさない。横操作で縦位置や行の高さを変えない。
- バーだけでなく、コード欄に対する横スクロール入力も共通の横位置を動かす。
  バーはマウスで操作でき、キーボードでもフォーカスして操作できる。
  バーを意図的に非表示にしない。OS・ブラウザによる自動非表示はその設定に従う。
- 横幅は表示したコードを実測して決める。幅計測のために全行を画面要素として
  生成しない。左右で最大の実測幅を共通の幅として記録する。
  まだ表示していない長い行の幅は、その行が表示されたときに初めて反映してよい。
- 同じファイルエントリを表示している間、縦移動、折りたたみの開閉、表示モードや
  折返しの切り替え、画面のリサイズでは記録した最大幅を縮めない。
  さらに長い行を表示したら最大幅とバーの移動範囲を広げ、現在の横位置は変えない。
  記録した最大幅がペインに収まる場合はバーを隠す。
- 横位置と最大幅は現在のファイルエントリを開いている間だけメモリに持つ。
  別のファイルエントリを選んだら両方をリセットする。元のファイルへ戻った場合も
  左端から始める。ページ再読込を越えて保存しない。
- 折返しを有効にすると、バーを隠し、コードの横移動を解除して折り返す。
  2 列表示の横位置は覚えておき、折返しを無効にしたら復元する。
  1 列表示へ移った間も 2 列表示の横位置を保持し、2 列表示に戻ったら復元する。
- 同じファイルエントリの内容更新、テーマ変更、ハイライトの切り替えでは、最大幅を
  捨てて表示中のコードから測り直す。横位置は可能な範囲で保つ。
  幅の測り直し・画面のリサイズ・横位置の復元で、横位置が移動可能範囲を超える場合は
  その末端に補正する。移動範囲が無い場合は左端に補正する。

**成功条件**

- 長さが異なる旧・新の行を 2 列・折返し無効で開き、下端のバーを操作すると、
  両側のコードが同量動き、各行の末尾まで読める。行番号・コメント・中央の境界は
  動かず、文字が隣のペインに重ならない（ブラウザ自動化と人の操作で確認）。
- 右へ移動した状態で縦スクロールやコメントの開閉をしても、作り直された行が
  同じ横位置で表示される（ブラウザ自動化で確認）。
- 短い行だけの場所へ縦移動してもバーの範囲が縮まず、未表示だった長い行が
  現れた場合だけ広がる。範囲が広がっても読んでいた横位置は変わらない。
- Wrap の ON→OFF、2 列→1 列→2 列で横位置が復元される。内容更新・テーマ変更・
  ハイライト切り替えでは再計測され、復元不能な横位置だけが末端に補正される。
- 別のファイルへ移ると左端から始まり、前のファイルの最大幅が残らない。
  幅の計測を含めても `R-VIEW` の 50 万行の操作性と行要素数の条件を満たす。

**反例**

- 長い行が見切れるが、横操作の入口が無く Wrap を有効にするしかない。
- 右へ移動しても短い行は左端のままで、旧・新の対応する横位置がずれる。
- 縦スクロールやコメント操作のたびに横位置が左端へ戻る。
- 長い行が画面外へ出るとバーの範囲が縮み、横位置が勝手に戻る。
- 折返し中もコードが横へずれたまま、またはコメントまで横へ動く。

## R-RENDER 描画表示

Markdown・表（CSV / TSV）・画像を、行の差分（ソース表示）ではなく描画した見た目
（描画表示）で読めるようにする。GitHub の rich diff に相当する。用語は `CONTEXT.md`
（描画表示 / ソース表示 / ブロック）。

**要件**

対象と切り替え

- 描画表示の対象は拡張子で決め、大小文字は区別しない。Markdown は `.md` / `.markdown`、
  表は `.csv` / `.tsv`、画像は `.png` / `.jpg` / `.jpeg` / `.gif` / `.webp` / `.svg`。
  改名では新側のパス、削除ファイルでは旧側のパスで判定する。
- 既定はソース表示。Markdown と表は、ファイルヘッダの "Rendered" / "Source" の
  切り替えとキー操作（割り当ては D15）で描画表示にする。ファイルごとの切り替えは
  ページを開いている間だけ覚え、セッションには入れない（復元でもソース表示に戻る）。
  ヘッダの他の操作と同じく、内容の取得が終わるまで切り替えは無効。
- 画像は切り替えを持たず、常に描画表示（`R-VIEW` のバイナリの規則の例外）。SVG だけは
  テキストなので切り替えを持ち、既定は描画表示（画像を並べる）、切り替えるとソース表示
  （テキストの差分）。
- 描画表示は表示モード（1 列 / 2 列）に関係なく 1 段で出す。画像だけ、2 列では旧と新を
  左右に、1 列では上下に並べる。
- 描画は表示時に計算する（`R-SERVE` の行データと同じ。起動時と `api/review` では
  計算しない）。
- 描画表示は行の仮想化と折りたたみを持たず、上限の範囲で文書全体を出す。

Markdown の描画

- 方言は GFM（表・取り消し線・タスクリスト・自動リンク・脚注）。`.mdx`、front matter の
  中身、数式は解釈しない（P18）。
- 先頭の front matter（1 行目がちょうど `---` で、その後にちょうど `---` だけの行が
  現れるまで）は切り離し、コード塊と同じ見た目の無地の塊として先頭に出す。閉じる
  `---` が無ければ front matter とみなさず、全体を Markdown として描画する。
- 生 HTML は解釈せず、テキストとしてエスケープして出す。
- リンクの `href` と画像の `src` は、前後の空白と制御文字を除いてから判定し、大小文字を
  区別しない `http` / `https` スキーム、`//` で始まらない相対パス、`#` 始まりだけを
  通す。それ以外（`javascript:` / `data:` / `//host` など）は無効にする。外部 URL の
  リンクは新しいタブで開き、`rel="noopener noreferrer"` を付ける。相対パスのリンクは
  リンクにせず、テキストとして出す（パスは `title` 属性で見える。kemi には飛び先の
  ページが無く、ページの URL 配下への遷移先をリポジトリの内容が作れないようにする）。
- コード塊は、そのファイルのハイライトの設定（`R-VIEW`）に従い、フェンスの情報文字列の
  言語でサーバ側にハイライトする。別の切り替えは持たない。
- 相対パスの画像は、その Markdown ファイルのディレクトリを基準に解決する。先頭の `/`
  はリポジトリの根。解決の元は、その画像を含むブロックの側の版で、入力モードごとに
  次のとおり（削除ファイルは全体が旧側のブロック）:

  | 入力モード | 新側のブロックの画像 | 旧側のブロックの画像 |
  |---|---|---|
  | worktree | 作業ツリーのファイル | `HEAD` |
  | staged | インデックス | `HEAD` |
  | コミット範囲（最終形） | `to` | `from` |
  | コミット範囲（コミットごと） | そのコミット | その親 |
  | manifest | レビュー対象の画像だけ | 同左 |
  | 復元 | 写しにある（レビュー対象の）画像だけ | 同左 |

  描画の時点で分かるもの（正規化した結果がリポジトリの外に出るパス、画像の拡張子で
  ないもの、manifest と復元でレビュー対象に一致しないもの）は `src` を出さず、alt
  テキストとパスを示す枠にする。レビュー対象の画像は、kemi がそのレビューで読んだ
  バイト列を配る（`R-SERVE`）。ファイルを読まないと分からないもの（symlink、上限を超えるもの、存在しない
  ファイル）は `src` を出し、エンドポイントが 404 を返したらページが同じ枠に差し替える。
- 外部 URL（`http:` / `https:`）の画像はブラウザがそのまま読む。プロキシは持たない
  （P20）。

変更の見せ方

- 描画するのは新側の文書で、旧側は消した範囲と、重ねられない書き換えの旧の範囲だけを
  描画して、新側の対応する位置に差し込む（削除ファイルは旧側の文書全体を描画する）。
  差分はソース表示と同じ行の整列から求め、ブロック（`CONTEXT.md`）に写す。
- ブロックの行レンジが行の整列の範囲に収まらないときは、その行を「対応する新の行が無く、
  変わっていない」として読む。全行がそうなった旧のブロックは、消したブロックとして
  差し込まない。
- 変更の無いブロックはそのまま出す。追加したブロックは追加色の左帯を付け、消した
  ブロックは元の位置に削除色の左帯で残す。
- 書き換えは、旧と新でブロックの種類と、中のインライン要素（リンク・強調・コードなど）
  の種類と順番が同じ「文のブロック」（段落・見出し・リスト項目）なら 1 つのブロックに
  重ね、消した語を削除色の取り消し線、足した語を追加色で示す。語の印は、旧のブロックと
  新のブロックのテキスト全体の語単位の差分から作る（行ごとの強調からは作らない）。
  それ以外（構造が違う文のブロック、コード塊、表の行）は、旧のブロックを削除色、
  新のブロックを追加色で上下に並べる。リストと引用は入れ物で、その中のブロックごとに
  上の規則を当てる。
- 追加だけのファイルは全ブロックが追加色、削除だけのファイルは全ブロックが削除色。
- すべてのブロックの要素（変更の無いものを含む）は `data-kemi-block` 属性を持つ。値の
  書式は契約で、`<side>:<start>-<end>`（`side` は `new` / `old`、行番号は 1 始まりで
  両端を含む。例 `new:12-15`、`old:3-3`）。重ねたブロックは新側のレンジを持つ。
  自動検査はこれを数える。
- 由来の行（`R-ORIGIN`）は描画表示では出さない。

表（CSV / TSV）

- 区切りは拡張子で決める（`.csv` は `,`、`.tsv` はタブ）。1 行が表の 1 行。`"` で囲んだ
  フィールドと、その中の `""` を解釈する。フィールド内の改行は解釈せず、`"` の対応が
  取れない行があるファイルは描画表示を出さない（P19。下の「上限と失敗」の経路）。
  列数が行ごとに違ってもそのまま出す。
- 1 行目は見出し行（`<th>`）。足した行・消した行・書き換えた行は Markdown と同じ色で、
  書き換えは旧の行を削除色、新の行を追加色で上下に並べる（セル単位の強調はしない）。

画像

- 画像として並べるのは、拡張子が画像で内容がバイナリと判定されたファイルと、拡張子が
  `.svg` のファイル。拡張子が画像でも内容がテキストのもの（Git LFS のポインタ、空
  ファイルなど）は今までどおりテキストの差分。manifest で `old` / `new` を文字列で
  与えた差分にも同じ判定をかける。入力モードは問わず、配るのは kemi がそのレビューで
  読んだバイト列（`R-SERVE`）。
- 表示できない画像（壊れたファイルなど。`<img>` の読み込みに失敗したもの）は、その側を
  バイト数だけの枠に差し替える。
  untracked の上限（`R-INPUT-3`、D6）を超えて内容を読まなかったファイルは、内容が
  無いので今までどおりバイト数の増減だけを示す。
- 旧と新を `<img>` で並べ、それぞれにバイト数を添える。追加と削除は片側だけを出す。
  改名だけでバイト列が同じときは 1 枚だけ出し、"unchanged" と添える。
- 片側が 5 MB を超えるときは、`R-VIEW` のバイナリと同じくバイト数の増減だけを示す。
  Markdown の相対パス画像の上限も同じ 5 MB。
- 画像のバイト列は token 配下のエンドポイントで配る（`R-SERVE`）。SVG は `<img>`
  経由でだけ出す（中のスクリプトを動かさない）。

コメント

- 描画表示のブロックにホバーすると `+` が出て、押すとそのブロックの元の行レンジへの
  行コメントになる（`R-COMMENT`。submit JSON は通常の行コメントと同じで、描画表示から
  付けたことは区別しない）。side は、新側にあるブロック（重ねたブロックを含む）は
  新側、消したブロックは旧側。複数ブロックの範囲選択は無い（P21）。
- 入力欄にはそのブロックの元の行を見せる。新側なら suggestion も書ける。
- 吹き出しはブロックの直下に出す。既存のコメントは、その行レンジに重なる最初の
  ブロックの直下に出し、どのブロックにも重ならないもの（ブロック間の空行など）は
  直前のブロックの直下、直前のブロックが無ければ文書の先頭に出す。
- 画像へのコメントはファイル全体のコメントだけ（ファイルヘッダから）。

移動と帯

- `n` / `p` は、変更の印の付いたブロックとコメントの位置を止まる場所とする（`R-NAV`）。
  スクロールバー横の帯も同じ位置を写し、押すとそこへ移る。

上限と失敗

- Markdown と表で、片側が 10,000 行超または 1 MB 超のファイル（`R-VIEW` のハイライトと
  同じ境界）、描画に失敗したファイル、表の `"` の対応が取れないファイルは描画表示を
  出さない。画像にはこの境界は効かず、5 MB の規則だけが効く。
- 事前に分かるもの（行数・バイト数・表の `"` の対応）は、切り替えを無効にして理由を
  ツールチップに出す。切り替えを押してから描画に失敗したものは、ソース表示のままにして
  ファイルヘッダに理由を出す。どちらも理由の文言は契約としない。ソース表示は通常どおり。

ライブリロードと復元

- 更新バッジと読み込み直しは `R-LIVE` のまま。読み込み直しても、そのファイルの
  描画表示の状態は保つ。読み込み直しで描画できなくなったファイルはソース表示に戻し、
  切り替えを無効にする。コメントの `outdated` は `R-COMMENT` の規則のまま。
- 復元では写しの内容から描画する（`R-SESSION`）。

**成功条件**

- `<script>`、`<img onerror>`、`<iframe>`、`javascript:` のリンクを含む Markdown を
  描画した HTML に、それらが要素や属性として現れない（Rust のユニットテスト。生成した
  HTML 文字列を検査する）。
- インライン要素の種類と順番が変わらない、段落の 1 語の変更で、その段落のブロックが
  1 つだけあり、消した語と足した語の両方の印を持つ（純粋関数のテスト）。
- リンクを平文にした差分で、その段落が旧と新の 2 ブロックになる（純粋関数のテスト）。
- front matter 付きの Markdown で、先頭に無地の塊が 1 つ出て、その行レンジが front
  matter の行と一致する。閉じる `---` が無い Markdown では塊が出ない（純粋関数の
  テスト）。
- CRLF と複数バイト文字を含む Markdown でも、各ブロックの `data-kemi-block` の行レンジが
  元の行と一致する（純粋関数のテスト）。
- 表の分割で、`"a,b"` が 1 フィールド、`""` が `"`、タブ区切りが `.tsv` で効き、
  対応の取れない `"` を含む行があると描画不可になる（純粋関数のテスト）。
- 画像エンドポイントの応答に `Content-Security-Policy: sandbox` と
  `X-Content-Type-Options: nosniff` が付く（統合テスト）。
- `[x](../a.md)` の相対リンクを含む Markdown を描画した HTML に、そのリンクの `<a>` が
  無い（Rust のユニットテスト）。
- `../` でリポジトリの外に出るパスと画像でない拡張子を参照する Markdown を描画した
  HTML に、その画像の `src` が無く枠がある（Rust のユニットテスト）。
- symlink、5 MB 超、存在しないファイルを参照する Markdown を描画し、その `src` を
  取得すると 404 になる（統合テスト。URL は描画した HTML から取り、形には依存しない）。
- `src` の取得が 404 になった画像がページで枠になる（ブラウザ自動化）。
- フィクスチャの Markdown を描画表示にすると、`data-kemi-block` の数と行レンジが
  期待どおりになる（ブラウザ自動化）。
- 描画表示から付けたコメントが submit JSON に行コメントとして入り、`quote` がその
  ブロックの元の行になる（ブラウザ自動化）。
- 片側 10,001 行の Markdown で切り替えが無効になる（ブラウザ自動化）。
- 復元した Markdown を描画表示にでき、相対パス画像はレビュー対象のものだけ出て、他は
  枠になる（ブラウザ自動化）。
- 描画側のコメントの操作感（`+` の出方、吹き出しの位置、入力欄に元の行が見えること）
  は人が確認する。

**反例**

- Markdown の生 HTML がそのまま出て、リポジトリの内容がページでスクリプトを動かす。
- 構造の同じ段落の 1 語の変更で段落が旧と新の 2 つに割れる、または構造の違う段落を
  無理に重ねて読めない見た目になる。
- 描画表示から付けたコメントが submit JSON で別の形になり、エージェントが行を
  特定できない。
- 相対パス画像のエンドポイントがリポジトリの外のファイルを配る。
- 直接開いた SVG のスクリプトが kemi の API を呼べる。
- 起動時に全 Markdown を描画して、10,000 ファイルで 1 秒を超える。
- 10,000 行超の Markdown を描画して、ページが固まる。
- 復元で git を読みに行って、当時の差分と食い違う画像を出す。

## R-NARROW 狭い画面

ビューポートの幅が 720px 未満の状態を「狭い画面」と呼ぶ（`CONTEXT.md`。720px 以上は
「広い画面」）。LAN 公開（`R-SERVE` の `--bind`）でスマホから開いたときに、読めて
コメントして submit できるようにする。判定は幅だけで、端末の種類やタッチの有無では
変えない。この節は、幅 720px 未満に限って `R-VIEW` / `R-RENDER` / `R-COMMENT` の表示と
入口の規定を上書きする。上書きしないものは各節のまま。

**要件**

広い画面を変えない

- 幅で変わる規則は 1 つのメディアクエリ（`max-width` 719.98px 相当）に集め、JS も同じ
  メディアクエリを `matchMedia` で見る。幅の測り方はこれで CSS と JS で一致する。
- 狭い画面でだけ使う要素（ツリーを開く操作、「…」のメニュー、シートの閉じる操作、
  2 段目のバー）は常に DOM にあり、広い画面では CSS で隠す。広い画面で見えている要素と
  操作は変えず、`R-VIEW` の上部バーとヘッダの成功条件は広い画面でそのまま成り立つ。
- 幅がしきい値をまたいだら、再読込なしにその場で切り替わる。表示モードと折返しの切り替えは
  `R-VIEW` の「作り直し」の規則（上端に見えていた行を残す）に従う。開いていた引き出しと
  シートは閉じ、選択中の範囲と入力中の下書きは保つ。

配置

- ファイルツリーは隠し、上部バーの操作で左から重ねる引き出しとして開く。中身（グループ、
  ディレクトリ、状態、増減数、ノイズ、重要、コメント件数、見た）は `R-VIEW` のまま。
  ファイルを選ぶか、引き出しの外を押すと閉じる。本文は全幅。
- 表示モードは常に 1 列。2 列への切り替えは出さない。広い画面に戻ると、覚えている
  表示モード（`R-VIEW`）に戻る。描画表示の画像は 1 列の規則で上下に並ぶ（`R-RENDER`）。
- 折返しの既定はオン。狭い画面での切り替えはページを開いている間だけ覚え、localStorage
  には入れない（`R-SERVE` の localStorage の用途は変えない）。広い画面の既定（`R-VIEW`）は
  変えない。
- 上部バーは 2 段。1 段目は `kemi` の名前、`title`、ツリーを開く操作、コメント件数付きの
  コメント一覧の入口、更新バッジ、「…」のメニューを開く操作。2 段目は、コミット範囲ではグループ単位の切り替え
  （`R-UNIT`）を左に、見たの進捗（`R-SEEN`）、承認と変更要求のボタン（`R-SUBMIT`）。
  表示の操作（折返し・重要のみ・変更量順・テーマ）は「…」の 1 つのメニューにまとめ、
  メニューの中では `R-VIEW` の並びで文字ラベルを付けて出す（メニューは小さな覆いで、
  シートにはしない）。2 段目が入りきらないときは、見たの進捗を数字だけにし、それでも
  入らなければ 3 段目に折り返す。送信ボタンとグループ単位の切り替えの文言は変えない。
  `subtitle` と `meta` は `title` を押すと開くシートに入れる（広い画面では `R-VIEW` の
  とおり上部に出る）。
- ファイルヘッダは追従し、1 行目はパス（収まらなければ先頭を省略記号で切り、末尾を
  見せる）、残りにヘッダの操作と印（`R-VIEW`。描画表示の切り替えを含む。長い note では
  折り返して行が増えてよい）。
- コメント一覧は画面いっぱいのシート（閉じる操作つき）で出す。中身は同じ。
- 吹き出しとコメントの入力欄は、本文の幅いっぱいから始める（行の位置からのインデントを
  付けない）。本文の約 72 文字の上限（`R-VIEW`）はそのまま。
- 吹き出しは既定で畳んだ札（`R-VIEW` の 1 行の札）で出し、付けた直後のコメントも
  `R-VIEW` の「開いた状態で出す」を適用せず、札のままにする。「…」のメニューの
  「Comments」の切り替えで、札ごと隠して本文だけにでき、切り替えはページを開いている間
  だけ覚える。隠している間もコメントの有無は行番号の欄のコメント色の線（`R-VIEW`）と
  上部バーの件数で分かる。コメント一覧のシートから選ぶと、隠している間でもそのコメント
  だけ吹き出しを開いて見せ、閉じると札に戻る（隠している間なら消える）。
- 変更間の移動の操作と帯（`R-NAV`）、由来の行（`R-ORIGIN`）、見たのチェック（`R-SEEN`）は
  変えない。キー操作も変えないが、表示モードのキー（`u` / `s`）は狭い画面では効かず、
  移動の操作のキーの表示は出さない（操作は同じ）。`n` / `p` でファイルをまたいでも
  引き出しは開かず、引き出しの中の開閉だけを `R-NAV` のとおり行う。

コメントの入口

- 行番号のタップで選ぶ。選択が無いとき、タップした行が 1 行の選択になり、その行に `+` が
  出る（ホバーを要しない）。選択があるとき、同じ側で表示中の連続した行の中の別の行番号を
  タップすると、その 2 行を両端とする範囲になり、`+` は範囲の最後の行に移る。それ以外の
  タップ（反対側の行番号、折りたたみをまたぐ行、3 つ目以降の行）は、その行を両端とする
  新しい 1 行の選択に置き換える。同じ行の再タップと、本文の中で行番号以外を押すことは
  選択を解除する（上部バーやファイルヘッダを押しても解除しない）。`+` を押すと
  `R-COMMENT` の入力欄が開き、入力欄が開いている間は解除せず、入力を取り消すと選択も
  解除する。範囲は左右
  どちらか片側の連続した行で、`R-COMMENT` の規則のまま。
- 狭い画面では、行番号の押し下げとホバーによる選択（広い画面のドラッグ）は働かない。
- 描画表示（`R-RENDER`）のブロックはタップで `+` が出る。
- 広い画面のホバーとドラッグ（`R-VIEW`）は変えない。

**成功条件**

- 幅 390px で開くと、ツリーが見えず、上部バーの操作で引き出しが開き、ファイルを選ぶと
  閉じてそのファイルが出る（ブラウザ自動化。ビューポートの幅を指定して開く）。
- 幅 390px で、2 列への切り替えが無く、行が折り返され、行番号のタップで `+` が出て、
  2 つ目のタップで範囲になり、付けたコメントが submit の JSON に行コメントとして入る
  （ブラウザ自動化）。
- 幅 390px で、コメントを付けると畳んだ札で出て開かず、「…」の「Comments」で札が
  消えて行番号の欄の色の線は残り、隠している間にコメント一覧のシートから選ぶとその
  コメントだけ開く（ブラウザ自動化）。
- 幅 1280px で開いたとき、`R-VIEW` の上部バーとヘッダの成功条件がそのまま成り立ち、
  狭い画面でだけ使う要素が見えない（ブラウザ自動化）。
- 幅を 1280px から 390px に変えると再読込なしに狭い画面の配置になり、戻すと元に戻る
  （ブラウザ自動化）。
- 幅で変わる規則が 1 つのメディアクエリ（CSS と `matchMedia`）に集まっている（差分の
  レビューで確かめる）。
- 実機のスマホで LAN 公開のページを開き、読む・コメントする・submit するまでできる
  （人による確認）。

**反例**

- 広い画面のどこかの見た目や操作が変わる。
- 狭い画面でツリーが本文を押しつぶす、または 2 列表示が選べて読めない。
- 行番号をタップしても `+` が出ない。
- 幅をまたぐたびに再読込が要る。

## R-UNIT グループ単位の切り替え

コミット範囲の「最終形」と「コミットごと」を、1 回の起動の中で切り替える。

**要件**

- 切り替えはコミット範囲モードにだけ出す。コミットが 1 つだけの範囲でも出す。
  manifest / worktree / staged には出さない。
- 起動時は `--group-by` の単位（既定 最終形）だけを作る。もう片方は `api/review` の
  最初の応答を返した後、裏ですぐ作り始める。切り替えた時点で未完成なら読み込み中と
  表示する。作るのに失敗したときは、切り替えを「作れなかった」表示（理由と再試行の
  操作付き）にしてレビューを続ける。この失敗ではレビューを終了コード 2 で終えない。
- 作った単位は作り直さず、切り替えは表示の差し替えだけにする（ライブリロードは
  除く、`R-LIVE`）。
- コミットごとの単位を作るときは git の呼び出しを並列にしてよい。並列度は D8。
  並列で作っている間も、表示中のファイルの取得（`api/file`）は 100 ms 以内に返す
  （範囲の標準フィクスチャ、開発機でのスモーク基準）。
- 見たはグループ単位ごとに別に持つ。最終形で見たを付けても、コミットごとの同じ
  パスのファイルは未読のまま（`R-SEEN`）。
- コメントは、付けたグループ単位のファイルにだけ表示する。submit JSON には両方の
  単位のコメントがすべて作成順で入り、`group_id` で区別する（最終形は `all`）。
  切り替えても、前の単位で付けたコメントは消えず、`outdated` にもならない
  （グループ単位の切り替えでは `outdated` は変わらない。`R-COMMENT`）。
- 単位を切り替えたときは同じパスのファイルを表示する。コミットごとへ切り替えた
  ときは、そのパスを含む最初のコミットのファイルにする。同じパスが無ければ先頭の
  ファイルを表示する。由来から移ったときは、そのコミットの同じファイルの該当行を
  表示する（`R-ORIGIN`）。

**成功条件**

- 200 コミット × 100 ファイルのフィクスチャ（`R-VERIFY`）で、コミットごとの単位を
  作る時間が 1 秒未満（release ビルド、`scripts/measure-range.sh` の `commit`、
  3 回の中央値）。開発機のスモーク基準で、扱いは `R-SERVE` の 1 秒と同じ。
- 最終形とコミットごとの両方でコメントを付けて submit すると、両方のコメントが
  入り、`group_id` がそれぞれ `all` とコミットの sha になる。
- 最終形で見たを付けたパスが、コミットごとでは未読のまま。
- 単位を切り替えて戻っても、コメントと見たが残る。
- 範囲の標準フィクスチャで、裏でコミットごとの単位を作っている間の `api/file` の最も遅い
  応答が 100 ms 未満（`scripts/measure-range.sh` の `busy`）。
- コミットごとの単位を作るのに失敗しても（例: 作成中に `--to` の ref が消える）、
  レビューが続き、切り替えに「作れなかった」表示が出る（人が確認）。
- manifest / worktree / staged のページに切り替えが出ない。

**反例**

- 切り替えると、前の単位で付けたコメントが消える、または `outdated` になる。
- 最終形で起動したのに、コミットごとの単位を作り終えるまで最初の表示が出ない。
- 切り替えのたびに単位を作り直して待たされる。
- 裏での作成の失敗で、読んでいる途中のレビューが終了コード 2 で終わる。

## R-ORIGIN 由来

最終形の各変更ブロックに、その変更を入れたコミットを示す。

**要件**

- 最終形の各変更ブロックのすぐ上の「由来の行」（`R-VIEW`）に由来を出す。由来は、
  そのブロックの新側の行を最後に変えた、範囲内のマージ以外のコミットすべてを、
  新しい順に、短い sha と件名で示す。新側の行のうち、範囲内のどのコミットにも
  マージにも当たらない行が一部あれば、見つかったコミットに「一部特定できない」を添える。
- 削除だけの変更ブロックは、消えた行ごとにその行を消したコミットを求め、見つかった
  コミットをすべて新しい順に出す。1 行でも決まらない行があれば「一部特定できない」を
  添え、1 行も決まらなければ「特定できない」とだけ出す。消したコミットは
  `git blame --reverse` 相当で辿る。横のブランチで消した行がマージで入った場合は、
  マージではなく、そのブランチで消したコミットを由来にする（マージのもう片方の親の
  側を、マージ基点から辿り直す）。この辿り直しはマージの入れ子 8 段までとし、それを
  超えた行と辿れない行は「特定できない」に数える。
- 由来の「範囲」は、コミットごとの単位と同じ `--from..--to` のマージ以外のコミット
  とする。範囲内のどのコミットにもマージにも当たらない行は、由来の無い行として数える
  （ブロックの一部なら「一部特定できない」を添え、全部なら「特定できない」とだけ出す）。
- マージ自体（衝突の解決）が変えた行・消した行は、由来に「マージ `<短い sha>`」と出す。
- 由来を押すと、そのコミットの理由（本文）が開く。コミットの由来には「このコミットで
  見る」操作を付け、コミットごとの単位の、そのコミットのグループへ移る（`R-UNIT`）。
  移り先の行は `git blame` が示す、そのコミット時点のパスと新側の行番号とし、削除
  だけのブロックでは、そのコミットの旧側の行とする。マージの由来は理由を開くだけで、
  移り先は持たない。
- 由来はファイルを表示した時に計算する。差分の表示は由来の計算を待たず、由来は
  計算できたものから後から付く。
- 1 ファイルの片側が 10,000 行超または 1 MB 超のときは由来を既定で出さず、
  そのファイルでだけ有効化できる（ハイライトと同じ上限）。
- 由来の計算に失敗したファイル（git の失敗など）は、そのファイルの由来の行に
  「特定できない」と出し、レビューは続ける。この失敗ではレビューを終了コード 2 で
  終えない（`R-SUBMIT`）。

**成功条件**

- 2 つのコミットが同じファイルの別の箇所を変えたフィクスチャで、各変更ブロックの
  由来がそれぞれのコミットになる。
- 1 つのコミットが行を消したフィクスチャで、その削除だけの変更ブロックの由来が
  そのコミットになる。
- 横のブランチで行を消し、それをマージで取り込んだフィクスチャで、その削除だけの
  変更ブロックの由来がマージではなくそのブランチのコミットになる。
- 新側の行の一部が範囲内のどのコミットにも当たらないブロックで、見つかった
  コミットに「一部特定できない」が添えられる。
- 範囲の途中で改名されたファイルで、「このコミットで見る」が、そのコミット時点の
  パスの該当行へ移る。
- 範囲より前のコミットや、範囲外のコミットが由来に出ない。
- 10,000 行超のファイルで由来が出ず、有効化すると出る。
- 由来の計算で git が失敗するファイルを表示しても、そのファイルの由来が「特定できない」に
  なり、レビューが続いて、付けたコメントを submit できる。

**反例**

- 由来の計算が終わるまで差分が表示されない。
- 起動時に全ファイルの由来を計算する。
- 由来を特定できない削除ブロックに、推測したコミットが断定として出る。
- 途中で改名されたファイルで、「このコミットで見る」が別のファイルや別の行へ移る。
- 1 ファイルの由来の計算の失敗で、レビュー全体が終了コード 2 で終わり、コメントが失われる。

## R-NAV 変更間の移動

**要件**

- 描画表示（`R-RENDER`）では、変更の印の付いたブロックの先頭と、コメントの吹き出しの
  位置（置き場は `R-RENDER`）を止まる場所とする。以下の規則はソース表示のもので、
  由来の行の括弧は描画表示には効かない。
- 変更ブロック（`CONTEXT.md`）とコメントの位置を「止まる場所」とする。止まる場所は、
  変更ブロックの先頭（最終形で由来の行があるときは、その由来の行）と、変更ブロックの外にある行
  コメントの範囲の最初の行。範囲の最初の行が変更ブロックの中にあるコメントは、その
  ブロックの先頭で一緒に止まったものとする。ファイル全体へのコメントは止まる場所に
  含めない。
- 差分の右下に「前の変更」「次の変更」の操作と、表示中のファイルの止まる場所の
  「現在 / 全体」の数を常に出す。キーは `n`（次）と `p`（前）。文字の入力欄に
  フォーカスがある間は、`n` / `p` / `v` を含むキー操作は働かない。
- 「現在」は、表示領域の上端から少し下に引いた基準線（距離は実装が決める）を最後に
  越えた止まる場所とし、移動の記録ではなく、そのときの表示の状態から毎回決める。
  上端が基準線とちょうど同じ止まる場所は、越えたものとして数える。
  末尾までスクロールしきってそれ以上進めないときは、見えている止まる場所をすべて
  通過済みとみなし、「現在」はそのファイルの最後の止まる場所になる。どの経路で
  末尾に達しても同じで、そこで `n` を押すと次のファイルへ移る（最後のファイルでは
  "This is the last change"）。`p` は、そこへ送ると実際に表示が上へ戻る止まる場所のうち
  最後のものへ移り、どれも戻らなければ前のファイルの最後の止まる場所へ移る（最初の
  ファイルでは "This is the first change"）。ファイルの途中では、これは現在の 1 つ前と同じ。
- 表示中のファイルの最後の止まる場所で `n` を押すと、次のファイルの最初の止まる
  場所へ移る。「次のファイル」はツリーに見えている順（変更量順の並べ替えと重要のみの
  絞り込みを反映し、グループをまたぐ）で決める。ツリーで畳まれたグループや
  ディレクトリの中のファイルも順に含め、移ったらツリーをそこまで開く。ノイズとして
  畳まれたファイル、バイナリ（`R-RENDER` の画像を含む）、止まる場所が 1 つも無い
  ファイル（改名だけなど）は飛ばし、見たのファイルは飛ばさない。最後のファイルの最後の止まる場所では移らず、"This is the last change" と出す。
  `p` はこれと対称で、最初のファイルの最初の止まる場所で "This is the first change" と出す。
- スクロールバーの横に、表示中のファイルの変更（追加・削除の色）とコメント
  （コメントの色）の位置を示す細い帯と、今見えている範囲の印を出す。帯を押すと
  その位置へ移る。コードの縮小表示はしない（`P3`）。

**成功条件**

- 止まる場所を求める純粋関数のテストで、変更ブロックの先頭、ブロック外のコメント、
  ブロック内のコメント、ファイル全体のコメントの扱いが上のとおりになる。
- 「現在」と `n` / `p` の移り先を求める純粋関数のテストで、ファイルの途中、末尾まで
  スクロールしきった状態、スクロールできない短いファイル、基準線ちょうどにある
  止まる場所の扱いが上のとおりになる。
- 最後のファイルの最後の止まる場所で `n` を押すと、移らずに "This is the last change" と
  出る（人が確認）。
- 50 万行のフィクスチャファイルで、帯の表示と `n` / `p` を使ってもスクロールが
  固まらない（人が確認。`R-VIEW` の条件に含める）。

**反例**

- `n` が最後の変更から先頭へ戻り、どこまで読んだか分からなくなる。
- 帯がファイル全体の行を DOM に描いて、50 万行で固まる。

## R-SEEN 見たと進捗

**要件**

- 見たは、ファイルヘッダの文字付きのチェック "Seen" とキー `v` で付け外しする。
- 「閲」の印を出すのは、グループのファイルをすべて見たとき（ツリーのグループ見出し）
  と、承認の完了画面だけ。ほかの場所では使わない。
- ツリーのファイル行は、左端のチェックで見たかどうかを示す。取り消し線は使わない。
- ツリーのグループ見出しに「見た数 / 全数」と進捗バーを出す。グループのファイルを
  すべて見たら、数の代わりに「閲」の印を出す。
- 上部に、表示中のグループ単位の全体の進捗（見た数 / 全数）を出す。
- 見たはグループ単位ごとに別に持つ（`R-UNIT`）。

**成功条件**

- グループのファイルをすべて見たにすると、そのグループ見出しに「閲」の印が出る
  （人が確認）。
- `v` で表示中のファイルの見たが切り替わり、ツリーと上部の進捗が同時に変わる
  （人が確認）。

**反例**

- グループのファイルをすべて見ても、グループ見出しが変わらない。
- 見たのファイル名が取り消し線で表示され、削除されたファイルと区別できない。

## R-COMMENT コメントと suggestion

**要件**

- コメントは行レンジ（左右どちらかの連続した行）またはファイル全体に付けられる。
  ファイル全体のコメントは行を持たない。描画表示（`R-RENDER`）から付けたコメントも、
  そのブロックの元の行レンジへの行コメントで、この節の規則と submit JSON の形は変わらない。
- 行番号は 1 始まり、両端を含む。旧側の行番号は旧ファイルの行番号を指す。
- 解決（resolve）と返信の UI は v1 では設けない。サーバの API はどちらも受理して
  よいが、v1 の UI からは送られないため `replies` は常に空、`resolved` は常に
  false になる。
- コメントにはファイル内容の変化に対する `outdated` 状態がある:
  - コメント作成時の行テキスト（`quote`）と、対象ファイルの内容ハッシュを保持する。
  - 内容ハッシュが変わっていたら「古いコメント」として表示する。
    **自動で行番号を付け替えはしない。**
  - 履歴の書き換えでコメントを付けたグループが消えたときも「古いコメント」とする
    （`R-LIVE`）。
- suggestion は「新側の行レンジを置換する文字列」として構造化して保持する。
  空文字は行の削除を意味する。挿入のみの提案は、隣接行を含む置換として表現する。
  **suggestion は新側の行コメントにだけ付く。旧側とファイル全体のコメントでは
  常に `null`。**
- suggestion をブラウザから適用する機能は持たない（`P8`）。受け取った JSON を
  使って適用するのはエージェントの仕事。
- コメントは編集と削除ができる。
  - 編集で変えられるのは本文と suggestion（新側の行コメントだけ）。行レンジ・
    `side`・`quote`・作成時の内容ハッシュ（`outdated` の判定基準）は変えない。
    行レンジを変えたいときは、削除して付け直す。
  - 削除は確認を 1 回挟む。削除したコメントは submit JSON に出ない。コメントの
    `id` は再利用しない。
- コメントが追加されたとき、人間向けのライブ表示を stderr に出す。
  この表示の文言は契約としない。

**成功条件**

- コメントを付けて submit すると、`R-SUBMIT` の JSON に、本文・解決状態・
  `quote`・`outdated`・suggestion が入っている（`replies` は空配列でよい）。
- コメント後にファイルを変更して submit すると、そのコメントの `outdated` が
  `true` になる。
- 旧側（削除された行）にコメントでき、その suggestion は `null` になる。
- 本文を編集して submit すると、編集後の本文が入り、行レンジと `quote` は作成時の
  まま。
- 削除したコメントが submit JSON に無く、その後に付けたコメントの `id` が削除した
  `id` と重ならない。

**反例**

- suggestion が自由文に埋め込まれ、機械的に適用できない。
- 内容が変わったのに古い行番号のまま最新の行として提示される。
- 編集で行レンジや `quote` が変わり、エージェントが元の位置を特定できなくなる。
- 削除したコメントが submit JSON に残る。

## R-FOCUS 重要の表示

kemi は重要度を推定しない。重要の印は実装したエージェント（manifest または
`--focus`）が付ける。kemi はそれを優先的に見せるだけだ。

**要件**

- `focus: true` のファイルにはバッジと `note` を表示する。
- グループの `watch` を "Watch" のラベルでグループ見出しに常に強調して表示する。
  `why` は見出しの下に畳んで置き、開ける（`R-VIEW`）。
- 「重要のみ表示」のフィルタは、ツリーのファイルを絞る（本文の表示は変えない）。
- kemi が自動で並び順や重要の印を変えることはない。人が変更量ソートのトグルを
  操作した時だけ並びが変わる。
- ファイルツリーと `R-DIGEST` にも `focus` を反映する。

**成功条件**

- `focus` を付けたファイルにバッジとノートが出て、フィルタで絞り込める。
- 変更量だけを理由に順序や印が自動で変わることはない。

**反例**

- kemi が変更量や拡張子から「重要そう」なファイルを自動で重要扱いする。

## R-SUBMIT 送信と契約

**要件**

- ページには "Approve" / "Request changes" の 2 つの送信ボタンと、任意のコメントがある。
  送信の前に、取り消せないことと verdict を確認するダイアログを挟む。確定した
  ときだけレビューを終了し、サーバは応答を返した後に停止して CLI が終わる。
  キャンセルでは何もしない。
- 確認ダイアログには、送るコメントの件数（うち suggestion 付きの件数、両方の
  グループ単位の合計）と、表示中のグループ単位の見たファイル数 / 全数を出す。
  見ていないファイルがあるときは、その数を注意として出す。
- 送信後の完了画面には、結果の JSON と、それをクリップボードへ写す操作、結果ファイル
  の保存先（`R-RESULT`）を出す。エージェントが反応しないときは、この JSON を会話へ
  貼れば済むと示す。承認のときは「閲」の印を出す。
- 送信後は承認と変更要求のボタンを無効にする。
- 同時に 2 つの submit が届いた場合、受理するのは 1 つだけとし、もう片方には
  409 を返す。受理して停止した後の再送は接続が拒否されてよい。
- CLI は終了時に stdout へ JSON 文書を 1 つだけ出力する。ログと URL は stderr に
  出す。stdout にそれ以外を混ぜない。同じ JSON を結果ファイルにも書く（`R-RESULT`）。
  セッションを消すのは submit を確定したとき（`R-SESSION`）。
- 終了コード: `0` 承認 / `1` 変更要求 / `2` 起動・使い方・実行時のエラー /
  `130` 利用者による中止（submit なしの Ctrl+C / SIGTERM の保留と、選択の取り消し。
  `R-SESSION`）。保留では stdout に何も出さず、セッションを残す。復元できる
  セッションが残るときは、保留でも実行時エラーでも、復元コマンドの 1 行を stderr に
  出す（`R-SESSION`）。レビュー中の git や I/O の失敗も `2` とし、stdout に JSON を
  出さない（このときもセッションは残る）。ただし、裏でのグループ単位の作成の失敗
  （`R-UNIT`）、由来の計算の失敗（`R-ORIGIN`）、結果ファイルの保存の失敗（`R-RESULT`）
  はレビューを終えず、終了コードも変えない。
- 出力する JSON の契約:

```json
{
  "kemi": 1,
  "title": "…",
  "verdict": "approved" | "changes_requested",
  "approval": [{ "path": "…", "identity": "sha256:…" }],
  "comments": [
    {
      "id": "c1",
      "group_id": "g1",
      "group_title": "…",
      "path": "src/a.rs",
      "side": "new" | "old",
      "start_line": 12,
      "end_line": 14,
      "quote": ["コメント時の行テキスト", "…"],
      "body": "本文",
      "replies": [],
      "resolved": false,
      "outdated": false,
      "suggestion": { "replacement": "置換後の全文" }
    }
  ]
}
```

- フィールドの規約:
  - `side` は `"new"` か `"old"`。ファイル全体のコメントは `"new"`。
  - `start_line` / `end_line` は 1 始まり、両端を含む。ファイル全体のコメントは
    `null`。
  - `quote` は `side` 側の対象行のテキスト（ファイル全体のコメントは `[]`）。
  - `suggestion` は無いとき `null`。旧側とファイル全体では常に `null`。
  - `replies` と `resolved` は全コメントに必ずある（無い場合は `[]` / `false`）。
  - `approval` は入力をそのまま返す。無い場合は `[]`。
  - `group_id` は `R-INPUT` の表の値。`group_title` はそのグループの `title`。
  - `comments` は作成順。`kemi` はこの契約の版（数値）。

**成功条件**

- 承認で終了コード 0、変更要求で 1 になり、stdout が 1 つの JSON として
  パースできる。
- コメント本文に改行や引用符があっても JSON が壊れない。
- 保留（Ctrl+C）では JSON が出ず、終了コード 130。セッションが残り、stderr の
  「resume with」の行のコマンドで同じレビューを続けられる（`R-SESSION`）。
- ファイル全体へのコメントが `start_line: null` / `end_line: null` /
  `quote: []` で出る。
- 送信後、承認と変更要求のボタンが押せない（ブラウザ自動化で確認）。
- 完了画面の JSON が stdout の JSON と同じ内容になる（人が確認）。

**反例**

- 進捗ログが stdout に混ざり、JSON のパースに失敗する。
- 同時 submit の両方が受理され、どちらの verdict か分からなくなる。
- 送信後もボタンが押せ、確認ダイアログの後に何も起きない。
- Ctrl+C でレビュー中のコメントが失われる。

## R-RESULT 結果ファイル

submit の結果を、エージェントが受け取り損ねても後から読めるように残す。

**要件**

- submit を確定したとき、stdout に出す JSON と同じ内容を結果ファイルに書く。verdict は
  問わない。保留（終了コード 130）とエラー（終了コード 2）では書かない。
- 置き場所は `$XDG_STATE_HOME/kemi/results/`。`XDG_STATE_HOME` が未設定か相対パスなら
  unix では `~/.local/state/kemi/results/`、Windows では `%LOCALAPPDATA%\kemi\results\`。
  `LOCALAPPDATA` も相対パスなら未設定と同じ扱いにする。Windows で `LOCALAPPDATA`
  も未設定なら決められず、unix で HOME が無い場合と同じ扱い
  （起動時に決められないエラー）にする。1 回の submit で 1 ファイルを作り、名前に送信時刻を
  含める。同じ時刻に送信したセッションがあっても名前は衝突しない。「最新」と「古い」は
  送信時刻（ミリ秒）で決める。ファイルとディレクトリの権限は unix のみ定める:
  ファイルは所有者だけが読み書きでき（`0600`）、ディレクトリは所有者だけが使える
  （`0700`）。Windows では `%LOCALAPPDATA%` の既定の ACL に任せ、特別な ACL 設定は
  行わない。
- 結果ファイルは、どのリポジトリのレビューだったかを識別できるように置く。識別の基準は、
  kemi を起動したディレクトリを含む git リポジトリのトップのディレクトリ。git の外なら
  起動したディレクトリそのもの。識別の情報はファイルの中身（JSON）に足さず、置き場所
  か名前で持つ（方法は D9）。
- 結果ファイルは全リポジトリ合計で新しい方から 20 件を残し、書くときにそれより古い
  ものを消す。
- 保存に失敗しても、stderr に警告を出し、完了画面に英語の保存失敗メッセージを出す
  だけで、stdout の JSON と終了コードは変えない。
- 保存先のディレクトリを、サーブ開始時に stderr へ出し、完了画面にも出す（文言は
  契約としない。`kemi: <url>` の行とは別の行にする）。
- `kemi --result` は、今いるリポジトリ（識別の基準は上と同じ。`--workspace <path>`
  で場所を指定できる）の最新の結果ファイルの中身を stdout に出して終わる。終了コードは
  元の verdict と同じ（承認 0 / 変更要求 1）。該当する結果が無ければ、stdout に何も
  出さず終了コード 2。`--any` を付けると場所に関係なく最新の結果を出す。

**成功条件**

- `XDG_STATE_HOME` を一時ディレクトリにして submit すると、stdout と同じ JSON の
  ファイルが unix では `0600` でできる。続けて同じディレクトリで `kemi --result` を実行すると、
  同じ JSON が出て、終了コードが元の verdict と一致する。
- Windows で `XDG_STATE_HOME` を未設定のまま `LOCALAPPDATA` を一時ディレクトリにして
  submit すると、その下の `kemi\results\` に同じ JSON のファイルができる。
- 21 回 submit すると、結果ファイルは 20 件で、最初の 1 件が消えている。
- リポジトリ A で submit した後、リポジトリ B で `kemi --result` を実行すると終了コード
  2 で何も出ず、`--any` を付けると A の結果が出る。
- 結果の置き場所に書けない状態で submit しても、stdout の JSON と終了コードが
  書ける場合と同じになる。

**反例**

- 別のリポジトリの結果を、今のリポジトリの結果として返す。
- 保存の失敗でレビューが終了コード 2 になり、stdout に JSON が出ない。
- 結果ファイルが消されずに増え続ける。
- 他の利用者が結果ファイルを読める権限で作られる（unix の権限条件。Windows では
  `%LOCALAPPDATA%` の既定 ACL に任せるため、この反例は適用しない）。

## R-SESSION セッションの保存と復元

未 submit のレビューをセッションとしてディスクに残し、あとから当時の差分のまま復元する。

**要件**

- 起動に成功したレビューは、submit するまでセッションとして残る。セッションは次を持つ:
  - 復元に使うレビューの写し。両グループ単位のレビューの全体で、ページの題
    （`title` / `subtitle` / `meta`）と `approval` を含み、変更ファイルの左右の内容を
    gzip で圧縮して持つ。内容にはバイナリ（`R-RENDER` の画像）も含め、下の上限に数える。
  - セッション状態（コメント、見た、折りたたみ、解決）。折りたたみはファイルごとの
    畳みの上書き（`R-VIEW`）とする。
  - セッションの情報（`id`、作成と最終更新の時刻、元のワークスペースのパスと識別、
    入力モードと範囲、`title`、起動時に開く方のグループ単位の全ファイル数）
- 置き場所は結果ファイルと同じ根の下の `sessions/`（決め方は `R-RESULT` と同じ。
  unix では `$XDG_STATE_HOME/kemi/sessions/`）。ファイルとディレクトリの権限も
  `R-RESULT` と同じ（unix はファイル `0600`、ディレクトリ `0700`）。
- `id` は 26 文字の ULID（例 `01K5...`）。同じ時刻に作っても衝突しない。一覧の並びは
  `id` の文字列ではなく、記録した最終更新の時刻で決める。
- 写しは、起動時に計算するメタデータと、`api/review` の最初の応答を返した直後に読む
  内容から作る（起動を待たせない）。両グループ単位のメタデータと内容がそろった時点で
  完成とする。
- コミット範囲のセッションは、起動時に解決した `from` と `to` の完全な sha を範囲と
  して書き、復元時の由来と「このコミットで見る」はその sha で計算する（`R-ORIGIN`）。
- セッション状態は変更のたびに書く。書き込みは一時ファイルから名前を変える原子的な
  差し替えとし、途中で失敗したファイルがセッションとして読まれないようにする。
  強制終了（kill -9）やクラッシュでも、最後に書けたところまでは残る。
- セッション状態の書き込みに失敗しても、レビューは終わらせない。stderr に警告を出し、
  終了コードも変えない（結果ファイルの保存の失敗と同じ扱い。`R-RESULT`）。
- 起動中のレビューはセッションのロックを取り、submit か保留で解放する。ロック中の
  セッションの `kemi --resume` は理由を stderr に出して終了コード 2。プロセスが
  残したロックは、記録した pid の生死で見分けて奪う。
- submit を確定したら、結果ファイルを書く（失敗は警告のみ。`R-RESULT`）→ セッションを
  消す → stdout に JSON を出す、の順で進める。
- 終了コード 130 は、保留（Ctrl+C / SIGTERM）と、選択の取り消し（Esc / Ctrl+C）の
  両方を指す（`R-SUBMIT`）。保留ではセッションを残し、復元できるセッションが残るときは
  stderr に機械が読む 1 行 `kemi: resume with: kemi --resume <id>` を出す。実行時
  エラー（終了コード 2）でも同じく、復元できるセッションが残るならこの行を出す。
  この行以外の案内の文言は契約としない。
- 写しが完成していない、または写しが上限を超えるセッションは、状態と情報だけを残し、
  一覧と復元の対象にしない（手で読めばコメントを回収できる）。id を指定した `--resume`
  は理由を stderr に出して終了コード 2。保存すべき状態が 1 つも無く写しも無い場合は、
  セッションを残さない。
- 写しの上限は 1 セッション 20 MB、全セッション合計 500 MB（どちらも圧縮後のバイト数。
  合計には状態と情報も含める）。セッションは全ワークスペース合計で、新しい方から
  100 件、または合計 500 MB の小さい方を残し、超えた分を最終更新の古い順に消す。
  掃除はセッションを書くときに行い、ロック中のセッションは消さず、合計にも数えない。
  復元できないセッションも件数と合計に数える。
- `kemi --resume [<id>]` で復元する。復元は同じ `id` のセッションを続けるもので、
  新しいセッションは作らない。`id` を指定したときは、そのセッションをどのディレクトリ
  からでも復元する。元のワークスペースが無くても復元できる。
  - `id` を省略したときは、標準入力が端末なら選択の画面（TUI）を出す。端末でなければ、
    復元できるセッションがあるときに限り、一覧を stdout に 1 行 1 件のタブ区切りで
    出して終了コード 0 で終わる。1 つも無ければ stdout に何も出さず、理由を stderr に
    出して終了コード 2。指定されていても、この起動では `--port` / `--bind` / `--no-open`
    を使わない（使い方の誤りにはしない）。
  - 一覧と選択の画面の行は、`id`、最終更新、ワークスペース、モード、見た数 / 全数の
    5 列。値に含まれるタブと改行は空白に置き換える。見た数は状態から数え、全数は
    起動時に開く方のグループ単位の値。並びは選択の画面と同じく最終更新の新しい順。
  - 選択の画面は、復元できるセッションだけを最終更新の新しい順に並べる。日時は
    ローカル時刻の `YYYY-MM-DD HH:MM`。モードは worktree / staged はその名前、
    コミット範囲は元の `from..to`、manifest は `title`。取り消し（Esc と Ctrl+C）では
    何も変えず終了コード 130。
  - 存在しない `id`、復元できないセッションの `id`、`R-INPUT-6` に反するフラグの
    組み合わせは、理由を stderr に出して終了コード 2。
- 復元したレビューは次のとおり:
  - 差分はセッションの写しだけから作り、元の入力（コミット範囲、worktree、manifest）を
    読み直さない。写しに無いファイルは作らない。
  - 見た、折りたたみ、コメント、解決は続きから始まる。ライブリロード（監視と更新
    バッジ）は出さない。表示モードとテーマはセッションに保存せず、ブラウザの
    localStorage に任せる（URL と token が変わる復元では初期値に戻りうる）。
  - 由来（`R-ORIGIN`）は、記録した範囲の sha を使って元のワークスペースの
    リポジトリから計算する。読めない場合はそのファイルの由来が「特定できない」に
    なり、レビューは続く。
  - `--port` / `--bind` / `--no-open` は通常の起動と同じに働く。URL と token は
    新しく作る（古い URL は使えない）。
  - submit の結果ファイルは、セッションの記録した元のワークスペースの識別で置く
    （`R-RESULT`）。復元したディレクトリは使わない。
- `--digest` と `--result` はセッションを作らない。
- 読めない形式の版のセッションは、理由を stderr に出して終了コード 2。黙って空の
  レビューを出さない。

**成功条件**

- `XDG_STATE_HOME` を一時ディレクトリにして `--worktree` で起動し、Ctrl+C で保留すると、
  stdout が空で終了コード 130、stderr の「resume with」の行に `id` があり、
  `kemi --resume <id>` で同じファイル一覧と内容のレビューが始まる。
- 保留の間にワークツリーのファイルを変えてから復元しても、表示される内容が変えた後の
  ものではなく、レビュー開始時のものである（人が確認）。
- 保留したセッションでコメントを付け、submit すると、結果ファイルが元のワークスペースの
  識別で置かれ、セッションが消える。
- manifest の `approval` を持つセッションを復元して submit すると、結果の JSON の
  `approval` が元の入力と同じ。
- セッションのファイルとディレクトリが unix で `0600` / `0700` になる。
- 写しが上限を超える、または完成しないまま保留すると、stderr に復元できない案内が
  出て、一覧にそのセッションが出ず、id を指定した復元は終了コード 2。
- 101 件目のセッションを書くと、最終更新が最も古いセッションが消える。合計が 500 MB を
  超える場合も同じ。ロック中のセッションは消えず、合計に数えない。
- セッション状態の書き込みを失敗させても、レビューが続き、終了コードが変わらない。
- 起動中のレビューの `--resume` が、理由を出して終了コード 2。
- `kemi --resume` を `id` なし・標準入力が端末でない状態で実行すると、一覧が 5 列の
  タブ区切りで stdout に出て、終了コード 0 で終わる。復元できるセッションが無ければ
  stdout が空で終了コード 2。
- 復元したレビューで元のワークスペースのリポジトリを消してから開くと、由来が
  「特定できない」になり、レビューは続く（人が確認）。
- 復元したレビューに更新バッジが出ず、元の入力が変わってもページの内容とコメントが
  変わらない（ブラウザ自動化で確認）。
- 読めない形式の版のセッションを復元すると、理由を出して終了コード 2。
- `kemi --digest` と `kemi --result` の前後で `sessions/` の内容が変わらない。
- `kemi --resume` に `--digest` を付けると終了コード 2。復元できるセッションが 1 つも
  無い `kemi --resume` は理由を出して終了コード 2。

**反例**

- 保留するとコメントが消える。
- 復元したレビューが、現在のワークツリーの内容を出す。
- 復元のたびに新しいセッションができ、同じレビューが一覧に増え続ける。
- 大きすぎるセッションが一覧に出て、選ぶと内容の欠けたページが開く。
- セッションが消されずに増え続ける、または他の利用者が読める権限で作られる。
- 復元したレビューの submit 結果が、復元に使ったディレクトリの識別で置かれる。
- 二つ目の復元が同じセッションに書き込み、コメントが混ざる。
- 元プロセスが動いているセッションを復元できてしまう。
- 復元したレビューに更新バッジが出て、写しと違う内容が表示される。
- 読めない版のセッションが、空のレビューとして黙って開く。

## R-DIGEST digest

**要件**

- `--digest` はページを出さず、レビューの地図だけを JSON として stdout に
  1 つ出して終了する（行内容は含めない）。コミット範囲では `--group-by` の単位
  （既定 最終形。グループは 1 つ）で集計する。
- 出力の契約:

```json
{
  "kemi": 1,
  "title": "…",
  "totals": { "files": 30000, "add": 123456, "del": 7890, "noise_files": 12000 },
  "groups": [
    { "id": "…", "title": "…", "why": "…", "watch": "…",
      "files": 10, "add": 100, "del": 20 }
  ],
  "directories": [
    { "path": "src", "files": 100, "add": 1000, "del": 200, "noise_files": 3 }
  ],
  "top_files": [
    { "path": "src/a.rs", "status": "modify", "add": 100, "del": 20,
      "noise": false, "focus": true, "note": "…" }
  ],
  "top_files_omitted": { "files": 0, "add": 0, "del": 0 },
  "top_n": 100
}
```

- `directories` はルート直下のディレクトリ単位で集約する。直下のファイルは
  `path` を `"."` とする 1 項目にまとめる。
- `top_files` は増減の合計（`add + del`）の降順、同数はパス昇順。件数は
  `--digest-top`（既定 100）を要求値とする。ただし出力全体の予算 100 KB に
  収まらない場合は、載せられなかった分を `top_files_omitted`（件数と増減の
  合計）にまとめる。切り捨てが無いときも 0 件で存在する。
- 文字列は 2,000 文字を上限とし、切った場合は末尾に `…` を付ける。
- 行内容や `quote` は含めない。30,000 ファイルの入力でも出力が 100 KB 未満に
  収まる。

**成功条件**

- 30,000 ファイルのフィクスチャで `--digest` の出力が 100 KB 未満で、
  `top_files` が増減合計の降順で入り、`top_files` と `top_files_omitted` の
  件数の合計が対象ファイル数と一致する（切り捨てが無ければ omitted は 0 件）。
- エージェントがこの JSON だけで「どこを読むべきか」を選べる（人が確認）。

**反例**

- `--digest` が全ファイルの一覧をそのまま出し、30,000 ファイルで数 MB になる。
- 行内容や `quote` が混ざる。
- 切り詰めた `why` に印が無く、完全な文と区別できない。

## R-LIVE ライブリロード

**要件**

- 監視対象は「レビューの新側の供給元」に限る:
  - worktree / manifest の `new_path`: 対象ファイル
  - コミット範囲: `--to` の ref（既定 `HEAD`）。ref の更新は検知の対象。
    それ以外の `.git` 内部の書き込みは無視する。
- 変更を検知したら SSE でブラウザに「更新あり」を知らせ、バッジを表示する。
- 再取得は人の操作で行う。勝手にスクロール位置や表示内容を変えない。
- 再取得後、内容が変わったファイルのコメントは `outdated` 表示にする（`R-COMMENT`）。
- コミット範囲では、作ってあるグループ単位を両方とも取り直す。見たとコメントは
  グループとパスが同じファイルに引き継ぐ。新しいコミットは、コミットごとの単位に
  未読のグループとして加わる。
- 履歴の書き換え（amend や rebase）でコミットごとのグループが消えたときは、そこに
  付いていたコメントを submit JSON に元の `group_id` と `group_title` のまま
  `outdated: true` で入れる。画面では、コメント一覧に「消えたコミット」として出す。
- 監視の追加・更新は debounce し、短期間の複数書き込みでバッジを点滅させない。
- 復元したレビューでは監視も更新バッジも行わない（`R-SESSION`）。

**成功条件**

- worktree モードでファイルを外部から変更すると、バッジが出て、押すと差分が更新
  される。
- 変更後にページのスクロール位置が勝手に変わらない。
- `--group-by commit` で `--to HEAD` の状態で新しいコミットを作るとバッジが出る。
- 再取得の後、コミットごとの単位に新しいコミットのグループが未読で加わり、既存の
  グループの見たとコメントが残る。
- amend でグループが消えた後に submit すると、そのグループのコメントが元の
  `group_id` のまま `outdated: true` で入る。

**反例**

- リポジトリ全体を再帰監視して、数万ファイルのリポジトリで監視が破綻する。
- 変更のたびに自動で再読込し、読んでいた位置を失う。
- 対象外の `.git` 書き込みでバッジが出続ける。

## R-WS 構成

```
Cargo.toml            # workspace + バイナリパッケージ kemi
rust-toolchain.toml   # Rust の版を固定
src/main.rs           # CLI 起動と配線、stdout/stderr、終了コード
crates/kemi-core/
  src/domain/         # 純粋なドメイン（差分整列、コメント、digest、ノイズ判定）
  src/source/         # git・manifest の読み取り（外部入力アダプタ）
crates/kemi-server/   # HTTP / SSE（axum）
crates/kemi-webview/  # HTML/CSS/JS 資産の埋め込み
web/
  package.json        # TypeScript（型チェックのみ）を固定
  tsconfig.json
  index.html
  assets/             # ビルド不要の ESM + CSS。app.js / features/ / views/ / leaf の
                      # 4 層（層の分け方は D11）
skills/
  kemi/SKILL.md       # エージェント向けの使い方（配布物。R-DIST）
scripts/
  gen-fixture.sh      # 検証用の合成リポジトリ生成
  measure-startup.sh  # 起動時間の計測
  measure-range.sh    # コミット範囲のグループ単位を作る時間の計測
```

- `kemi-core` の `domain` は純粋関数で、axum / hyper / tokio / `std::process` に
  依存しない（`source` モジュールはこの限りでない）。層は
  domain → source → server/cli の一方向。
- `kemi-server` は `kemi-core` に依存する。`kemi-webview` はどこにも依存しない。
  ルートのバイナリが 3 つを配線する。
- フロントはビルドなしのネイティブ ESM と CSS。型は JSDoc で書き、CI で
  `tsc --checkJs --noEmit` を通す（型チェックのみで生成物を出さない）。
  純粋なロジックは `node --test` でテストする。
- Node と Rust の版はリポジトリ内で固定する（`.mise.toml` / `rust-toolchain.toml`）。
- 資産は release ビルドでバイナリに埋め込み、開発時はディスクから配る。

**成功条件**

- `cargo build` だけで（Node 無しでも）バイナリができる。
- `rg 'use (axum|hyper|tokio|std::process)' crates/kemi-core/src/domain` が
  import 行に一致しない。
- `npx tsc -p web --noEmit` と `node --test web` が成功する。

**反例**

- ドメインが git コマンドや HTTP の型を直接参照する。
- フロントのビルドに Node が必須で、クリーンな `cargo build` が失敗する。

## R-DEPS 依存

調査済みの推奨スタックを使う（`D5`）。互換のため、同じ役割の別クレートに
差し替えても上の要件を満たすなら変更してよい。

- 差分整列: `similar`（単語単位の強調を含む）
- 構文ハイライト: `syntect` + `two-face`。`syntect` は `default-features = false` と
  `default-fancy` を使い、oniguruma（C 実装）に依存しない。計画時に
  `cargo tree -e features` で C 依存が無いことを確認する
- HTTP / SSE: `axum`
- 資産埋め込み: `rust-embed`
- ファイル監視: `notify`（debounce は固定の時刻で試せるよう自前で持つ）
- JSON: `serde` / `serde_json`
- 乱数（URL トークン）: `getrandom`（C 依存を持ち込まない）
- セッションに保存する内容の圧縮: `miniz_oxide`（pure Rust。C 依存を持ち込まない）
- 端末の選択画面: `inquire`（pure Rust）
- Markdown の構文木: `ox_content_ast` + `ox_content_parser` + `ox_content_allocator`
  （ox-content、MIT、pure Rust）。HTML はブロックごとの属性と語の印のために kemi が
  自分で書き、ox-content の描画器は使わない。計画時に `cargo deny check licenses` と
  `cargo tree` で依存の木を確認する。表（CSV / TSV）の分割は自前で持つ

許可する依存ライセンスは MIT / Apache-2.0 / BSD-3-Clause / ISC / Unicode-3.0 と
その互換（0BSD 等）に限る。

**成功条件**

- `cargo deny check licenses` が成功する。
- `cargo tree -e features` に oniguruma 系の C 依存が現れない。

**反例**

- GPL 系ライセンスのクレートが混入する。
- musl 静的リンクが C 依存で失敗する。

| 条件 | 出所 |

- `scripts/gen-fixture.sh <dir> --files N --lines M [--commits K]` は、決定的な
  内容で git リポジトリを生成する（同じ引数なら同じ結果）。
- `scripts/measure-startup.sh <fixture> <kemi-bin>` は、release ビルドの kemi を
  `--port 0 --no-open` で起動し、stderr の `kemi: <url>` 行を待って
  `api/review` を取得するまでの時間を計測し、3 回の中央値を表示する。
- `scripts/measure-range.sh <fixture> <kemi-bin> <commit|file|busy>` は、release
  ビルドの kemi をフィクスチャの最初のコミットからの `--from` で起動して計測する。
  `commit` / `file` は `--group-by <commit|file>` で起動し、`api/review` を取得する
  までの時間の 3 回の中央値を表示する。`commit` の時間を、コミットごとの単位を作る
  時間とみなす（同じ処理のため。`R-UNIT`）。`busy` は既定（最終形）で起動し、
  `api/review` の直後から、裏でコミットごとの単位を作っている間に最初のファイルの
  `api/file` を 10 回取得し、最も遅い応答時間を表示する（`R-UNIT` の 100 ms）。
  このスクリプトで使う「範囲の標準フィクスチャ」は
  `scripts/gen-fixture.sh <dir> --files 100 --lines 20 --commits 201`（最初のコミットの
  後に 200 コミット）。
- 時間の上限（1 秒、および `R-UNIT` の 100 ms）は開発機でのスモーク基準とする。
  計測の対象は `scripts/gen-fixture.sh` が作るフィクスチャで、追加主体の worktree は
  対象外（許容する）。CI では余裕を持った閾値にし、マシン差を理由に失敗し
  続けないようにする。

**成功条件**: 上のコマンドがすべて成功する。

**反例**: 目標の規模で 1 秒を大きく超える、またはテストが環境依存で
恒常的に不安定。

## 委譲

- D1 CLI 表面の細部（`R-INPUT-6` に書いた契約以外のフラグ名、エラーメッセージ、
  モード排他時の文言）。
- D2 テーマプリセットの具体的な配色（`R-VIEW` の役割ごとの色を含む）。
- D3 リリースパイプラインの道具立て（cargo-dist、GitHub Actions）。
- D4 submit JSON の残余の細部（`id` の形式、ライブ表示の文言）。骨格は
  `R-SUBMIT` が契約。
- D5 クレート選定（`R-DEPS` の範囲内）。
- D6 ノイズ判定の具体パターン、untracked のサイズ上限の値、行ハイライトの
  キャッシュ方式。存在と意味は契約、値は動作を変えない範囲で実装が決める。
- D7 内部 HTTP API の JSON 形（`R-SERVE` のエンドポイント以外の形）と、`R-SERVE` の
  一覧に無いエンドポイントの追加。どちらも画面の振る舞いを変えず、ページと
  サーバの間でだけ使う。
- D8 コミットごとの単位を作るときの git 呼び出しの並列度。どの値でも表示される内容は
  同じで、`R-UNIT` の時間条件と「表示中の操作を遅らせない」を計測しながら満たす値を
  実装が探る。
- D9 結果ファイルの名前の形式と、リポジトリの識別を置き場所と名前のどちらでどう持つか。
  どの方法でも `R-RESULT` の選び方（送信時刻で決める最新、リポジトリの識別の基準）と
  中身は同じ。
- D10 スキル（`skills/kemi/SKILL.md`）と README の Agent skill の節の、言い回しと見出しの
  構成。`R-DIST` の「含むもの」を欠かさず、契約と食い違わない限り、どの書き方でも
  振る舞いは同じ。手順だけで submit まで到達できることは `R-DIST` の成功条件が縛る。
- D11 フロントの層の分け方（`web/assets/` の 4 層と依存の向き）。規則の置き場は
  `PROJECT.md`。どの分け方でも画面の振る舞いは変わらず、`R-WS` の成功条件（`tsc` と
  `node --test`）で検査する。
- D12 セッションのファイル形式（写しと状態と情報の分け方、gzip した内容の入れ方、形式の
  版の持ち方）。どの形式でも `R-SESSION` の上限、掃除、復元の内容は同じ。
- D13 セッションのロックの実装（ロックのファイル名と、残ったロックを奪う判定の細部）。
  どの実装でも二重復元は防がれ、強制終了の後に復元できる。
- D14 端末の選択画面の見た目の細部と、`id` の生成方法。どちらも `R-SESSION` の形式と
  並びを満たす限り、どの実装でも同じ。
- D15 描画表示とソース表示を切り替えるキーの割り当て。既存のキー（`n` / `p` / `v`）と
  衝突しなければ、どのキーでも振る舞いは同じ。
- D16 描画結果のキャッシュ。持っても持たなくても画面は同じで、`R-SERVE` の「起動時に
  計算しない」を守る限り実装が決める。

## 却下

- R1 名前 `diff-review` の継承（理由: kemi を選択）。
- R2 静的 HTML 書き出し（理由: 大規模初期表示とコメント機能の両方で不利）。
- R3 テーマカスタム編集 UI（理由: プリセットで足りる）。
- R4 ブラウザ内編集（理由: レビューが目的。編集はエージェントが行う）。
- R6 suggestion のブラウザ適用（理由: 自分では直さない方針）。
- R7 ツールを変えず、旧 `diff-review-viewer` スキルに `--group-by file` か manifest を使わせるだけにする
  （理由: 最終形とコミットごとの両取りに届かない）。
- R8 両取りを起動時の `--group-by` の選択だけで済ませる（理由: 見せ方を変えるたびに
  起動し直しになる）。
- R9 コミットごとの単位を、切り替えを押したときに初めて作る（理由: 最初の切り替えで
  待たされる）。
- R10 コメントを行の印とポップアップだけで表示する（理由: コメントが常に隠れ、送信前の
  見直しに別の一覧が要る）。
- R11 変更間の移動の単位をハンクにする（理由: 1 つのハンクに複数の変更が入り、読みたい
  所に止まらない）。
- R12 コミットごとで付けたコメントを最終形にも写す（理由: その行が最終形に残るとは
  限らず、行の対応が一意に決まらない）。
- R13 削除だけの変更ブロックに由来を出さない（理由: 消した理由も判断の材料になる）。
- R14 digest だけコミットごとを既定に残す（理由: 同じ引数で画面と digest の単位が
  食い違う）。
- R15 結果ファイルを消さずに増やす、または 1 件だけ残す（理由: 前者は際限なく増え、
  後者は同時に動かしたセッションの結果を上書きする）。
- R16 結果の読み出しをサブコマンド `kemi result` にする（理由: 位置引数の manifest
  パスと区別できない）。
- R17 スキルを plugin 経路（Claude Code / Codex の marketplace の定義ファイル）でも配る
  （理由: 単体のスキルに対して、エージェントごとの定義ファイルと版の写しが要り、手間に
  見合わない。コピー経路は定義ファイル無しで動く）。
- R18 submit を止める read-only モード（理由: 公開は同僚に kemi を体験してもらうのが
  目的で、押せない UI は要らない。最初の submit でレビューが終わるのは既存の契約の
  まま）。
- R19 アクセス元で submit の可否を変える（理由: ループバック限定は公開の目的に反し、
  判定の基準も増える）。
- R20 セッションの写しを差分パッチとして持ち、復元時に old 側を再構成する（理由:
  復元の実装が重く、失敗したときの被害が大きい）。
- R21 復元のときに元の入力を読み直し、変わっていたら現在の内容を出す（理由: 当時の
  差分を再現できず、コメントの `quote` と表示が食い違う）。
- R22 同じセッションを二重に復元できるようにする（理由: コメントが混ざる）。
- R23 ページに保留ボタンを置く（理由: プロセスを落とす運用と相性が悪く、状態の保存が
  操作に依存する）。
- R24 選択を番号の入力だけにする（理由: 選ぶ操作を矢印で行える対話の体験を優先した）。
- R25 旧の描画と新の描画を 2 列に並べる（理由: 変更点を目で探すことになり、差分を読む
  道具として弱い）。
- R26 Markdown を開いたとき描画表示を既定にする（理由: GitHub と同じくソースが既定で、
  suggestion を書くにはソースが要る）。
- R27 Markdown の中の相対パス画像を出さない（理由: GitHub の rich diff に合わせ、
  スクリーンショット入りの文書を読めるようにする）。
