# エージェントとのやりとり 仕様

- Status: 草稿（ライブ改訂）
- 用語の定義: `CONTEXT.md`
- 本体の仕様: [kemi 仕様](kemi.md)。動いているページのレビューは [live.md](live.md)
- 見た目の参照: `docs/design/ui-mock-conversation.html`（採用したモック。案 A2）。エージェントの
  状態の見せ方、渡した後の作業中の行、別のスレッドの新着の知らせは
  `docs/design/ui-mock-live-v2.html`（`--live` の使い勝手の見直しで採用したモック）。モックと
  この仕様が食い違うときは仕様が正しい。

結果を一文で: **レビューを 1 回の submit で終えるまでの間に、人間とエージェントがコメントの
返信とレビュー全体への発言で何往復もやりとりできるようにする。**

各要件の「成功条件」と「反例」の書き方は [kemi 仕様](kemi.md) の冒頭と同じ。証拠の出所は
[R-VERIFY](kemi.md#r-verify-検証)。

## R-AGENT-FLOW 往復の流れ

**要件**

- 1 回のレビューは何往復しても 1 回の起動のまま続き、submit（承認か変更要求）で終わる。
  submit の受理が 1 回だけであること、終了コード、stdout の JSON は
  [R-SUBMIT](kemi.md#r-submit-送信と契約) のまま。
- 人間はコメント・返信・発言を書き、「エージェントに渡す」でまとめてエージェントへ届ける
  （[R-AGENT-HAND](#r-agent-hand-渡す)）。エージェントは `kemi wait` で受け取り、`kemi reply`
  で返信・発言・案を書く（[R-AGENT-CLI](#r-agent-cli-kemi-wait-と-kemi-reply)）。
- エージェントが一度も `kemi wait` を呼ばないレビューは、今までどおり submit だけで
  やりとりする。画面の「エージェントに渡す」は押せないまま、`kemi wait` を始めると渡せることを
  示す（[R-AGENT-STATE](#r-agent-state-エージェントの状態)）。
- この流れは入力モードを問わない（manifest・コミット範囲・worktree・staged・`--live`）。

**成功条件**

- worktree モードで起動し、`kemi wait` を呼んでから画面でコメントを書いて渡すと、
  `kemi wait` がそのコメントを返す。`kemi reply` で書いた返信が画面のスレッドに出る。
  その後 submit すると、kemi 本体が今までどおり stdout に JSON を出して終わる（e2e）。
- `kemi wait` を一度も呼ばずに起動したレビューの画面で、「エージェントに渡す」が出ていて
  押せない。その後 submit すると、今までどおり stdout に JSON を出して終わる（ブラウザ自動化と e2e）。

**反例**

- 渡すたびにレビューが終わり、起動し直しになる。
- `kemi wait` を使わない今までのエージェントで、レビューの終え方が変わる。

## R-AGENT-HAND 渡す

**要件**

- コメント・返信・発言は、書いた時点ではエージェントに届けない。「エージェントに渡す」を
  押したとき、前に渡した後に起きた変化（コメントの追加・編集・削除、返信、発言）を
  まとめて 1 回分として届ける。
- 渡した後に本文を編集したコメントは、次に渡すときに届き、編集済みであることが分かる。
- 人間はスレッドの中で返信を書け、どのコメントにも属さないレビュー全体への発言を
  書ける。どちらも書いた人（人間）を持つ。
- 解決（resolve）は人間だけが行える。解決したスレッドは自動で畳み、開き直せる。
  解決していないスレッドも畳める。畳んだスレッドは、会話パネルの一覧の項目も差分の中の札も
  1 行（解決したものは解決済みの印つき）に縮め、押すと普通どおり開く（[R-VIEW](kemi.md#r-view-差分の表示)）。
- まだ渡していないコメント・返信・発言が残ったまま submit するときは、確認の中に
  その件数を出す。submit は止めない（結果にはすべて入る）。解決していないスレッドが
  残っていても承認は止めない。
- 返信・発言が届いたとき、会話パネルの並び（開いたスレッドの並びも含む）は、一番下を
  見ているときだけ新しいものが見えるところまでついていく。上のほうを見ているときは位置を
  変えず、新しいものが届いたことを示す。差分のスクロール位置はどちらの場合も変えない
  （[R-LIVE](kemi.md#r-live-ライブリロード)）。
- スレッドを開いているときに別のスレッドへ返信が届いたら、開いているスレッドの上に、どの
  スレッドに届いたかを知らせ、押すとそのスレッドを開く。会話パネルを開いている間も、パネルの
  見出しに新着の数（数え方は [R-VIEW](kemi.md#r-view-差分の表示) の帯の新着の数と同じ）を出す。
- 渡した 1 回分の行: 渡したら、その 1 回分に入ったスレッドそれぞれの末尾に、エージェントの受け取りを
  待っていることを示す行を出す。発言だけの 1 回分（スレッドを含まない）は、会話パネルの並びの末尾に
  出す。
  - `kemi wait` がその 1 回分を返したら、行をエージェントが作業中であることを示すものに変える。
  - スレッドにエージェントの返信が届いたら、そのスレッドの行だけを消す（同じ 1 回分のほかの
    スレッドの行は残る）。発言だけの 1 回分の行は、エージェントの発言が届いたら消す。
  - 1 つのスレッドの行は 1 つで、行が残っているスレッドをまた渡したら、受け取り待ちに戻す。
  - 人間がコメントを消したら、そのスレッドの行も消す（受け取り待ち・作業中とも。保留と復元を
    またいでも戻らない）。エージェントは消したコメントに返信できないため。
  - 画面は行に `data-kemi-hand-line` 属性を付け、値は `pending`（受け取り待ち）か `working`（作業中）。
    属性と値は自動検査のための契約で、行の文言（画面モック）とは別。

**成功条件**

- コメントを 2 つ書いて渡すと、`kemi wait` の 1 回の応答に 2 つとも入る。書いただけで
  渡していない間は `kemi wait` が返らない（e2e）。
- 渡した後に本文を編集して渡し直すと、そのコメントが編集済みとして届く（e2e）。
- 未渡しのコメントを残して submit を押すと、確認に件数が出て、submit の JSON に
  そのコメントが入る（ブラウザ自動化）。
- 会話パネルの一番下を見ているときに `kemi reply` で発言を書くと、その発言が見えるところまで
  並びが進む。上のほうを見ているときに書くと、並びの位置は変わらず、届いたことを示す印が出る。
  どちらでも差分のスクロール位置は変わらない（ブラウザ自動化）。
- スレッド c1 を開いている間に `kemi reply` で c2 に返信を書くと、開いているスレッドの上に
  c2 に届いた知らせと、会話パネルの見出しに新着の数が出る。知らせを押すと c2 のスレッドが開く
  （ブラウザ自動化）。
- `kemi wait` が待っていない間に c1 を渡すと、c1 のスレッドの末尾に `data-kemi-hand-line="pending"`
  の行が出る。`kemi wait` を呼ぶとその 1 回分が返り、行が `working` になる。`kemi reply` で c1 に
  返信を書くと、その行が消える（ブラウザ自動化）。
- c1 と c2 を 1 回分で渡し、`kemi wait` が返った後に c1 にだけ返信を書くと、c1 の行は消え、c2 の
  行は `working` のまま残る（ブラウザ自動化）。
- 発言だけを書いて渡すと、会話パネルの並びの末尾に行が出て、`kemi reply` でエージェントの発言を
  書くと消える（ブラウザ自動化）。

**反例**

- 1 つ目のコメントを書いた瞬間にエージェントが動き出し、書きかけの意図で直される。
- 別のスレッドを読んでいる間に届いた返事に気づかず、エージェントの答えを見落とす。
- 渡した後に画面のどこにも動きが無く、渡せたのかエージェントが動いているのか分からない。
- エージェントがまだ受け取っていないのに「作業中」と出て、人間は何も起きていないことに気づけない。
- 2 つのスレッドを渡し、片方にだけ返事が来たのに両方の行が消え、もう片方が置き去りになる。
- 上のほうの発言を読んでいる最中に返信が届き、並びが一番下へ飛んで読んでいた場所を見失う。
- エージェントが解決を付け、人間が見ないうちにスレッドが閉じる。

## R-AGENT-CLI kemi wait と kemi reply

**要件**

- 起動したレビューは stderr に `kemi: review <id>` の 1 行を出す。`<id>` はセッションの
  `id`（[R-SESSION](kemi.md#r-session-セッションの保存と復元)）と同じ。この行は契約とする。
- セッションを作れなかったレビュー（状態の置き場所が決まらない、書けないなど）は、この行を
  出さず `<id>.endpoint` も作らない。往復は使えず、エージェントが一度もつながらないレビューと
  同じになる（[R-AGENT-FLOW](#r-agent-flow-往復の流れ)）。
- `kemi wait <id> [--timeout <秒>]`:
  - 前の `kemi wait` が返した後に起きたこと（渡された 1 回分、案の選択、submit）を
    すべて、JSON 1 つにして stdout に出して終わる（[R-AGENT-EVENTS](#r-agent-events-wait-が返す-json)）。
    起きたことが無ければ待ち続ける。
  - 起きたことに submit が含まれるとき、その JSON に submit の結果（stdout に出すのと
    同じ JSON）を入れ、終了コードは submit と同じ（`0` 承認 / `1` 変更要求）。それ以外で
    返すときは `0`。
  - `--timeout` の秒数が過ぎたら、stdout に何も出さず終了コード `3`。指定しなければ
    待ち続ける。
  - submit を確定したら、kemi は待っている `kemi wait` に submit の結果を渡し終えてから
    止まる。
  - 待っている間にレビューが保留か実行時エラーで終わったら、その `kemi wait` は理由を
    stderr に出して終了コード `2`。
  - レビューが動いていない（保留中、`id` が無い）ときは、理由を stderr に出して終了コード `2`。
    submit で終わった後に呼ばれたときも終了コード `2` で、レビューが終わったことと、結果は
    `kemi --result`（[R-RESULT](kemi.md#r-result-結果ファイル)）で読めることを stderr に出す。
  - 起きたことは失わない代わりに、同じものが二度届くことがある（出し終えた後、受け取ったことを
    レビューに知らせる前に止まったとき。次の `kemi wait` が同じ起きたことをもう一度返す）。
    エージェントはコメント・返信・発言の `id` で重なりを見分ける。
  - 同じレビューに同時に 2 つの `kemi wait` が来たら、後から来た方を理由つきで終了コード `2`
    にする。起きたことを 2 つに分けて配らない。
- `kemi reply <id>`:
  - 標準入力から JSON を 1 つ受け取り（[R-AGENT-WRITE](#r-agent-write-reply-の入力と上限)）、
    書けたら書いたものの `id` の一覧を JSON で stdout に出して終了コード `0`。
  - 1 件でも上限を超えるか形が誤っていれば、1 件も書かず、理由を stderr に出して終了
    コード `2`。
  - レビューが動いていないときは、理由を stderr に出して終了コード `2`。
- 最初の引数が `wait` か `reply` ならサブコマンドとして扱う。その名前の manifest を開くときは
  `./wait` のようにパスで書く。
- `kemi wait` と `kemi reply` は、ほかのフラグや入力モードと組まない。組んだら使い方の
  誤りとして終了コード `2`。
- `kemi wait` と `kemi reply` が話しかけられるのは、同じマシンの同じユーザーだけ
  （[R-AGENT-LINK](#r-agent-link-つなぎ先と安全)）。

**成功条件**

- `kemi --worktree --no-open` の stderr から `kemi: review <id>` を取り出し、その `id` で
  `kemi wait` と `kemi reply` が働く（e2e）。
- 状態の置き場所を決められない環境（unix で `XDG_STATE_HOME` も `HOME` も無い）で起動すると、
  stderr に `kemi: review` の行が無く、submit は今どおりできる（e2e）。
- `kemi wait <id> --timeout 1` が、起きたことが無ければ 1 秒後に stdout 空・終了コード 3 で
  終わる（e2e）。
- 画面で承認すると、待っていた `kemi wait` が submit の結果を入れた JSON を出して終了
  コード 0、変更要求なら 1 で終わる（e2e）。
- 存在しない `id` の `kemi wait` と `kemi reply` が終了コード 2（e2e）。
- 上限を超える件を 1 つ含む `kemi reply` が終了コード 2 で、画面に何も増えない（e2e）。

**反例**

- `kemi wait` が submit を見逃し、レビューが終わったのに待ち続ける。
- `kemi reply` が途中まで書いて失敗し、半分だけ画面に出る。
- 2 つの `kemi wait` がそれぞれ起きたことの一部だけを受け取る。

## R-AGENT-EVENTS wait が返す JSON

**要件**

- `kemi wait` が出す JSON の契約:

```json
{
  "kemi": 2,
  "review": "01K5…",
  "events": [
    {
      "type": "handed",
      "comments": [{ "change": "added" | "edited" | "deleted", "comment": { "…": "R-SUBMIT のコメントと同じ形" } }],
      "replies": [{ "comment_id": "c1", "reply": { "…": "R-SUBMIT の返信と同じ形" } }],
      "messages": [{ "…": "R-SUBMIT の発言と同じ形" }]
    },
    { "type": "chosen", "comment_id": "c1", "reply_id": "r2", "variant_id": "B" },
    { "type": "submitted", "result": { "…": "R-SUBMIT の JSON と同じ" } }
  ]
}
```

- `events` は起きた順。`handed` は「エージェントに渡す」1 回分、`chosen` は案の「これにする」
  （[live.md の案](live.md#r-page-variant-案)）、`submitted` は submit。
- `deleted` のコメントは `id` だけを持つ。
- コメント・返信・発言・submit の結果の形は [R-SUBMIT](kemi.md#r-submit-送信と契約) と同じで、
  ここに写さない。`kemi` は [R-SUBMIT](kemi.md#r-submit-送信と契約) と同じ結果 JSON の契約の版。

**成功条件**

- 渡したコメントの `comment` が、submit の JSON の同じコメントと同じキーを持つ（e2e）。
- ページへのコメントの描き込みの画像は、`kemi wait` の応答でだけ絶対パスで受け取れる。submit の
  結果では `null`（[R-SUBMIT](kemi.md#r-submit-送信と契約)）。
- `kemi wait` を呼ばずに案を選び、続けて渡してから `kemi wait` を呼ぶと、1 つの応答の
  `events` に `chosen` と `handed` が起きた順に並ぶ（e2e）。

**反例**

- `kemi wait` と submit でコメントの形が違い、エージェントが 2 通りの読み方を持つ。

## R-AGENT-WRITE reply の入力と上限

**要件**

- `kemi reply` が標準入力で受け取る JSON の契約:

```json
{
  "writes": [
    { "type": "reply", "comment_id": "c1", "body": "本文",
      "variants": [{ "label": "案 A", "note": "説明", "replace": [{ "selector": "…", "html": "…" }], "css": "…" }],
      "applied": { "reply_id": "r2", "variant_id": "B" } },
    { "type": "message", "body": "本文" }
  ]
}
```

- `reply` はコメントへの返信。`variants` と `applied` は任意で、`--live` のレビューでだけ
  受け付ける（それ以外では形の誤りとして終了コード 2。[live.md の案](live.md#r-page-variant-案)）。
  `message` はレビュー全体への発言。
- 案の `id` は、`variants` に並べた順に kemi が `A`、`B`、`C`… と振る。`applied` は案を
  反映したことを知らせる新しい返信に付け、反映した案を持つ返信の `id` と案の `id` を指す。
- エージェントはコメントを立てられず、解決を付けられない。
- 書いた返信と発言は、書いた人としてエージェントを持つ。
- 上限（これを超える書き込みは [R-AGENT-CLI](#r-agent-cli-kemi-wait-と-kemi-reply) のとおり 1 件も書かない）:
  - 1 つのコメントへのエージェントの返信: 50 件
  - エージェントのレビュー全体への発言: 200 件
  - 1 つの返信の案: 8 個
  - 1 つの案の置き換え（`replace`）: 8 か所
  - 本文 1 つ: 64 KB（UTF-8 のバイト数）
  - 案 1 つの中身（`replace` の `html` と `css` の合計）: 256 KB
- 上限の数字は暴走したエージェントがページとセッションを潰さないための目安で、測って
  決めたものではない。
- 成功したときの stdout の契約: `{ "ids": ["r3", "m1"] }`（`writes` と同じ順）。
- `writes` が空の `kemi reply` は断らない。何も書かず、終了コード 0 で `{ "ids": [] }` を出す。
  エージェントの状態も、応答なしまでの 10 分も変えない
  （[R-AGENT-STATE](#r-agent-state-エージェントの状態) の「書き込みが届く」に当たらない）。

**成功条件**

- `reply` と `message` を 1 つずつ書くと、画面の会話パネル（スレッドと発言の並び）に出て、stdout の
  `ids` が 2 つ（e2e とブラウザ自動化）。
- 存在しない `comment_id` への返信、`--live` でないレビューへの `variants`、51 件目の返信、
  64 KB を超える本文が、それぞれ終了コード 2 で何も書かない（e2e）。
- 渡して `kemi wait` が時間切れで返った後（作業中）に `writes` が空の `kemi reply` を送ると、終了
  コード 0 で `{ "ids": [] }` が出て、状態は `working` のまま（e2e）。

**反例**

- エージェントの返信が際限なく増え、ページが重くなりセッションが上限を超える。
- エージェントがコメントを立てて、人間のコメントとエージェントの書き込みが見分けられない。
- 何も書かない `kemi reply` で状態が「返事済み」になり、人間が届いていない返事を探す。

## R-AGENT-STATE エージェントの状態

**要件**

- 画面にエージェントの状態を出す。状態は 5 つ。

| 状態 | 意味 |
|---|---|
| 未接続 | このレビューで `kemi wait` が一度も呼ばれていない（始まりの状態） |
| 待機中 | `kemi wait` が待っている（渡せる） |
| 作業中 | `kemi wait` が返った後で、エージェントの返事を待っている |
| 返事済み | 最後に返った `kemi wait` が返した 1 回分に、エージェントが返事を書き終えた（人間の番） |
| 応答なし | 作業中のまま 10 分、`kemi wait` も `kemi reply` も来ていない |

- 状態は次の表のとおりに移る。表に無い組（たとえば返事済みで 10 分たつ）では状態を変えない。
  「返った」は時間切れで返ったときと、待っていた `kemi wait` の接続が切れたときを含む。
  「残りの行」は、最後に返った `kemi wait` が返した 1 回分の行のうち、まだ消えていないもの
  （[R-AGENT-HAND](#r-agent-hand-渡す)。時間切れで返ったときは無い）。「書き込みが届く」は、1 件以上を
  書いた `kemi reply` のこと（`writes` が空の `kemi reply` は届いたことにしない。
  [R-AGENT-WRITE](#r-agent-write-reply-の入力と上限)）。

| 今の状態 | 起きたこと | 次の状態 |
|---|---|---|
| どれでも | `kemi wait` が始まる | 待機中 |
| 待機中 | `kemi wait` が返る | 作業中 |
| 作業中・応答なし | `kemi reply` の書き込みが届き、残りの行が無くなった（または初めから無い） | 返事済み |
| 作業中・応答なし | `kemi reply` の書き込みが届き、残りの行がまだある | 作業中（10 分は数え直す） |
| 作業中 | 10 分、`kemi wait` も `kemi reply` も来ない | 応答なし |
| 未接続・待機中・返事済み | `kemi reply` の書き込みが届く | 変えない（行は [R-AGENT-HAND](#r-agent-hand-渡す) のとおり消える） |
| 待機中以外（未接続では押せない） | 人間が渡す | 変えない（渡した 1 回分は受け取り待ちの行で示す） |
| 待機中 | 人間が渡す | 待機中（`kemi wait` がすぐに返り、上の行のとおり作業中になる） |
| 作業中・応答なし | 人間がコメントを消し、残りの行が無くなった。最後に返った `kemi wait` の後に `kemi reply` の書き込みが 1 件以上届いている | 返事済み |
| 作業中・応答なし | 人間がコメントを消し、残りの行が無くなった。最後に返った `kemi wait` の後に `kemi reply` の書き込みがまだ届いていない | 変えない |

- 返事済みは、何分たっても応答なしにしない（エージェントは返事を書き終えて、人間の番になって
  いるため）。
- 画面は今の状態を `data-kemi-agent-state` 属性に出す。値は `not-connected`（未接続）・`waiting`
  （待機中）・`working`（作業中）・`replied`（返事済み）・`no-response`（応答なし）のどれか。属性と
  値は自動検査のための契約で、画面の文言とは別。
- 画面の状態の言い方は、人が次に何をすればよいかが分かるものにする: 待機中は渡せること、
  返事済みは返事が届いたことが読み取れる（文言は画面モック。UI の文言は英語。
  [R-DIST](kemi.md#r-dist-名称と配布)）。
- 「エージェントに渡す」は、状態によらず常に出す（会話パネルを畳んでいても見える）。未接続の
  間は押せず、エージェントが `kemi wait` を始めると渡せることと、そのコマンドを写す操作を
  そばに出す。写すコマンドはこのレビューの `id` を含む `kemi wait <id>`（そのまま貼れば動く。
  `id` は stderr にも出していて秘密ではない。[R-AGENT-CLI](#r-agent-cli-kemi-wait-と-kemi-reply)）。
  一度でも `kemi wait` が呼ばれたら押せる。ただし渡すもの（前に渡した後の変化）が無い間は、押せない
  見た目にして、渡すものが無いことを示す。
- 狭い画面（[R-NARROW](kemi.md#r-narrow-狭い画面)）では、どの入力モード・見方でも、「エージェントに
  渡す」を画面の下に浮かぶボタンとして出す（`--live` のページの見方では道具のツールバーの中。
  [live.md](live.md#r-page-view-ページの見方)）。会話パネルのシートを開かなくても渡せる。
- この節と [R-AGENT-HAND](#r-agent-hand-渡す) の画面の約束は、[R-AGENT-FLOW](#r-agent-flow-往復の流れ)
  のとおり入力モードを問わない（`--live` の画面で決めたものも全モードに効く）。
- 応答なしでもレビューは止めない。表示だけ。
- 状態の変化は SSE で画面に届ける（[R-SERVE](kemi.md#r-serve-配信モデル) の `api/events`）。
- この節と [R-AGENT-HAND](#r-agent-hand-渡す) の画面の変更（使い勝手の見直しで足したもの）を実装する
  コミットで、`skills/kemi`（`references/conversation.md` の「渡す操作は `kemi wait` の後にだけ出る」
  という記述と状態の説明）、README、CHANGELOG も同時に直す（[R-DIST](kemi.md#r-dist-名称と配布)）。

**成功条件**

- c1 を書いておき、`kemi wait` の前・最中、渡して返った後、`kemi reply` で c1 に返信した後、次の
  `kemi wait` で、`data-kemi-agent-state` が `not-connected`・`waiting`・`working`・`replied`・
  `waiting` と変わる（ブラウザ自動化）。
- c1 と c2 を 1 回分で渡して返った後、c1 にだけ返信すると `working` のままで、c2 にも返信すると
  `replied` になる（ブラウザ自動化）。
- 返事済みの間に渡しても状態は `replied` のままで、受け取り待ちの行が出る（ブラウザ自動化）。
- c1 と c2 を 1 回分で渡して返った後、c1 にだけ返信してから人間が c2 を消すと、c2 の行が消えて
  `replied` になる。c1 と c2 を渡して返った後、何も書かれないうちに c2 を消すと、`working` のまま。
  c2 を渡してから消し、保留して復元しても、c2 の行は戻らない（Rust のユニットテストとサーバの
  テスト。時刻は注入する）。
- 状態の移り方は、表の各行を純粋な関数のテストで確かめる。時刻を差し替えて、作業中のまま 10 分
  たつと応答なしになり、返事済みのまま 10 分たっても返事済みのまま（Rust のユニットテスト。現在
  時刻に依存させない）。
- 渡した直後は「エージェントに渡す」が押せず、返信を 1 つ書くと押せる（ブラウザ自動化）。
- 幅 390px の worktree のレビューで、会話パネルのシートを閉じたまま、画面の下の「エージェントに
  渡す」で渡せる（ブラウザ自動化）。
- `kemi wait` の前は「エージェントに渡す」が押せず、`kemi wait` を始めると渡せることと
  コマンドを写す操作が出て、写したものが `kemi wait <id>`（このレビューの `id`）になる。会話パネルを畳んでも「エージェントに渡す」が見える。`kemi wait` を
  呼ぶと押せるようになる（ブラウザ自動化）。

**反例**

- エージェントが落ちた後も「作業中」のままで、人間が待ち続ける。
- エージェントが返事を書き終えた後も「作業中」のままで、人間が返事に気づかず待ち続ける。
- 返事を待っていたコメントを人間が消したら、もう返事の来ない行が残り、「作業中」から
  「応答なし」になる。
- `kemi wait` の前に「エージェントに渡す」がどこにも無く、何をすれば渡せるのか分からない。
- 渡すものが無いのに押せて、押しても何も起きない。
- 狭い画面で、渡すたびに会話パネルのシートを開かなければならない。
- 状態の移り先が決まっていない組があり、実装ごとに表示が違う。

## R-AGENT-LINK つなぎ先と安全

**要件**

- エージェント用の API は、`--bind` に関わらず `127.0.0.1` で待ち受ける（`--bind` が具体
  アドレスでも、同じマシンの `kemi wait` が届くように）。
- 起動したレビューは、`kemi wait` と `kemi reply` がサーバに届くための情報（エージェント用の
  ポートとトークン）を `<id>.endpoint` に書く。unix ではセッションの置き場所に `0600` で置く。
  Windows では `XDG_STATE_HOME` の設定に関わらず `%LOCALAPPDATA%\kemi\sessions\` に置き、
  ユーザーごとのフォルダの既定の権限をもって持ち主だけとする。
- `<id>.endpoint` は submit・保留・実行時エラーで終わるときに消す。強制終了で残ったものは、
  そのセッションのロックが生きていなければ無いものとして扱う。
- エージェント用の API を守るのはトークンの秘密: ページのトークンとは別の値で、
  `<id>.endpoint` にだけ書き、ページにも stderr にも出さない。加えて、接続元がループバックで
  `Origin` を持たない要求だけを受理する（ブラウザの `POST` を確実に断るため）。

**成功条件**

- `--bind 0.0.0.0` で起動しても、LAN 側のアドレスからエージェント用の API に届かない
  （統合テスト。接続元を差し替える）。
- `Origin` を付けたエージェント用の API の要求が 403 になる（統合テスト）。
- `--bind` に LAN の具体アドレスを指定して起動しても、同じマシンの `kemi wait` と `kemi reply`
  が働く（e2e。アドレスはテストから差し替える）。
- 中継した開発中のページから、`fetch`（`no-cors` を含む）と `<img>` でエージェント用の API を
  呼んでも、書き込みが起きない（ブラウザ自動化）。
- `<id>.endpoint` が unix で `0600` になり、submit の後に無い（cargo test）。

**反例**

- URL を知っている人が LAN から `kemi reply` と同じ要求を送り、エージェントのふりをして
  書き込む。
- 中継した開発中のページの JS がエージェント用の API を呼ぶ。

## 作らないもの

- PA1 MCP サーバとしての接続。つなぎ方は `kemi wait` / `kemi reply` だけ。
- PA2 エージェントがコメントを立てる・解決を付ける機能。
- PA3 人間ごとの区別（著者）。書いた人は「人間」か「エージェント」かだけ（[P5](kemi.md#作らないもの)）。

## 委譲

- DA1 エージェント用 API の URL と内部の形、`<id>.endpoint` の中の形。どの形でも
  [R-AGENT-LINK](#r-agent-link-つなぎ先と安全) の受理条件と、CLI と JSON の契約は同じ。
- DA2 返信と発言の `id` の形式（[D4](kemi.md#委譲) と同じ扱い）。

## 却下

- RA1 MCP でつなぐ（理由: エージェントごとに対応と設定が違い、サーバ側から会話に知らせる
  仕組みが使えるか分からない）。
- RA2 コメントを書いた時点で 1 つずつ届ける（理由: 書きかけの意図でエージェントが動く）。
- RA3 `kemi reply` を引数（`--body` など）で書く（理由: HTML を含む案の受け渡しで引用符の
  扱いが壊れやすい）。
- RA4 返事を待っていたコメントを消しても状態を変えない（理由: 返事を書き終えた後も作業中のままで、
  10 分で応答なしになる）。
- RA5 コメントを消したときの返事済みの判定を、その 1 回分のスレッドへの返信だけで数える（理由: 状態の
  表の「書き込みが届く」とそろわない）。
- RA6 `writes` が空の `kemi reply` を形の誤りとして断る（理由: 害が無く、今の振る舞いを変える得が無い）。
