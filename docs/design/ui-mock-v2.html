2. コミット単位のグループは分かりやすいか 仕様判断

観測
今回の範囲（27 コミット / 35 ファイル項目）で、web/assets/app.js が 27 グループ中 21 グループに出てくる。最初のコミット（c01e476）の後に app.js を触ったコミットが 20 件あり、c01e476 の時点と最終形を比べると 90 行が消えるか書き換わっている（git diff --numstat c01e476 f65473c で +327 −90）。最初のグループで読んだ行の一部は、最終形には残っていない。
判断
コミットがきれいに分かれている（squash や rebase で整理済み）ならコミット単位は分かりやすい。「修正コミットが積み重なったブランチ」をまとめて見るには向いていない。manifest（エージェントが意図ごとに書くグループ）は各ファイルを 1 回だけ出せるので、この問題は起きない。
選択肢
A（推奨） ファイルごとに最終形を 1 回だけ出し、各変更の塊（ハンク）に「その行を最後に変えたコミット」を由来する。コミットの理由（本文）は由来から開ける。R-INPUT-2 の変更と、表示時の git blame 相当の計算が要る。
B ツールは変えず、ブランチ全体を見せるときは skill が --group-by file か manifest を使うよう決める。今日からできるが、--group-by file ではコミットの理由が消える。
C 現状維持（コミット単位のまま）。
分かれ目
レビューしたいのが「各コミットが何をしたか」なら C、「ブランチの最終形が正しいか」なら A か B。エージェントの作業ブランチをまとめて承認する使い方は後者なので A を推す（採用時は A と C の両取りに決まった）。ただし A は実装が一番重い。

案 A の見た目 — ハンクの見出しに由来コミットを出す（複数のコミットが触った塊には複数並ぶ）。クリックでそのコミットの理由が開く

5. コメントで差分が分断される 設計変更 仕様判断（編集・削除）

観測
コメントは画面幅いっぱいの灰色の帯で、上下に罫線が付く。本文は幅の制限がなく、1600px 幅の画面では 1 行が 115 文字まで伸びた。複数行を選んだコメントは範囲の最初の行の直下に入る（model.js:439）ので、選んだ範囲の途中でコードが割れる。「あなた」の札は 1 人で使う道具では情報がない。
併せて
付けたコメントを直す・消す手段がない（サーバが受け付けるのは追加・返信・解決のみ、crates/kemi-server/src/api.rs:460-480）。誤字もそのままエージェントへ渡る。追加には R-COMMENT の変更が要る。

現状（実際のスクリーンショット、試しに付けたコメント）

同じ内容で案を比べる

  • 案 1: 範囲の最後の行の下に、コードの位置から始まる付箋色の吹き出し。尾が対象行を指し、範囲の行は行番号の左端に付箋色の線。既定は 1 行の札に畳み、クリックで開く。畳んだ札は 1 行ぶんしか押し下げない。
  • 案 2: 差分には行を足さない。行番号の横に印だけを出し、クリックで右側に吹き出しが浮く。コードは一切ずれないが、コメントが常に隠れていて、浮いた吹き出しがコードに重なる。
  • 推す理由: 案 1 はコードの流れを 1 行ぶんしか崩さず、しかも付けたコメントが常に目に入る。案 2 は分断ゼロだが、送信前に自分のコメントを見直すには別の一覧が要る。

6. 承認しても黙って終わる 設計変更 仕様判断（結果の保存）

仕組み
送信を確定するとサーバが止まり、結果の JSON が標準出力に 1 回だけ出て kemi が終わる（src/main.rs:288-300）。結果はメモリにしか無いので、エージェントがその出力を受け取っていなければ消える。ページ側は「JSON を出力して終了しました」と出すだけで、受け取られたかは分からない。
一番疑わしい原因
エージェント向けの手順書 ~/.claude/skills/diff-review-viewer/SKILL.md が旧ツール向けのままで、「The command keeps running until interrupted」（中断するまで動き続ける）と書いてある。これを読んだエージェントは kemi が自分で終わることも、終わったときに JSON を読む必要があることも知らない。TODO.md の「納品後の環境更新」に更新が残っている。ただし、落ちた回にエージェントが実際にどう起動していたかは確認できていない（推測）。
提案
まず手順書を直す（kemi 本体は変えない）: バックグラウンドで起動して終了通知を待ち、終わったら標準出力の JSON を読む、と書く。
ページ側（仕様内）: 確認ダイアログにコメント件数と未読ファイル数を出す。完了画面に結果の JSON と「コピー」ボタンを出し、エージェントが反応しないときは会話に貼れるようにする。送信後は承認ボタンを無効にする（今は押せてしまい、確認ダイアログが出た後に何も起きない）。
要判断: 結果をファイルにも残し、後から kemi --result で読めるようにする。「標準出力が唯一の出口」（R-SUBMIT）と「セッションはメモリのみ」（R-SERVE）に反するので仕様変更になる。手順書の修正で落ちなくなるなら不要。

7. 色が単調 設計変更

今は GitHub の配色（灰色と青 1 色）そのままで、「選択中」「押されたボタン」「リンク」「展開ボタン」がすべて同じ青。意味ごとに色を分ける。差分の緑と赤は慣習どおり残し、ほかの意味に赤系を使わない（削除と見分けがつかなくなるため）。上部バーのアイコンは仕様（R-VIEW）どおりモノクロのまま。

一か所だけ遊ぶ: 名前の由来「閲する」から、グループを見終えたときと承認したときに藍色の「閲」の印を押す。

意味色使う場所今
藍（進捗・見た・主操作） 見たのチェック、進捗バー、閲の印、選択中のファイル、変更の見出し青 1 色が全部を兼ねる
付箋（コメント） 吹き出し、コメント件数、位置の帯の印、範囲の線灰色の帯
藤（重要・見てほしい点） 重要バッジ、見てほしい点の枠黄土色（付箋色と取り合うので移す）
追加 行・行番号の欄・変更箇所行番号の欄に色なし
削除 同上同上
  • ツリーの状態表示は、どのファイルにも付く「変更」の札をやめ、1 文字にして「変更」だけ薄くする。珍しい状態だけが目立つ。モックは GitHub と同じ A / D / R / M にしたが、仕様の「UI に英語の未翻訳文言を混ぜない」（R-DIST）に触れるかもしれないので、「追 / 削 / 改 / 変」でもよい。
  • コミットの種類（feat / fix など）は色を付けず小さな枠で区別するだけにした。色を増やしすぎると、上の意味の色が効かなくなる。
  • 書体は今のシステムフォントのまま。単一バイナリに書体を埋め込むとサイズが増えるわりに、見辛さの主な原因とは見ていないため（ここは未検証の判断）。
