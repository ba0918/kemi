# 2列表示の同期横スクロール

## 目的と仕様

長い行を、行番号やコメントの位置を保ちながら左右同時に横へ送って比較できるようにする。
正典は `docs/spec/kemi.md` の `R-VIEW-HSCROLL`。関連する `R-VIEW`、`R-LIVE`、
`R-WS` も読む。仕様の承認コミットは `5051263`。
この計画の作成から実装・レビューまで進めることはユーザーから一括で依頼されている。

## 方針と理由

既存の仮想描画（表示付近の行だけを作る方式）を維持する。コードだけの横位置と
実測幅を、再描画で消える行要素から分離する。下端の操作部は行要素の外に置く。
横操作だけで `renderDiff` を呼んで全行を作り直さない。

再利用の判断は、位置と幅の境界計算には既存の純粋関数層、状態には既存の state、
スクロール入力と幅計測にはブラウザ標準機能、縦の表示範囲には既存の仮想描画を採用する。
新しいランタイム依存やフロントのビルド工程は加えない。
共通幅を短い行にも適用する方法、コードの内側の要素構造、同じ画素量を反映する
仕組みは実装で選んでよいが、選択とコピー、ハイライト、入力操作を壊さないこと。

## 変更範囲

- `web/assets/model.js`、`model.test.js`: 横位置・最大幅の純粋な計算。
- `web/assets/state.js`: 現在のファイルエントリの横状態。
- `web/assets/features/display.js`、`files.js`、`theme.js`: 描画・再計測・ファイル変更の接続。
- `web/assets/views/diff-rows.js`: コードと固定領域の分離。
- `web/assets/style.css`、`web/index.html`、`web/assets/dom.js`、`app.js`: 下端の操作部とイベント。
- 必要なら `web/assets/features/horizontal-scroll.js` と
  `web/assets/horizontal-scroll.js` / `horizontal-scroll.test.js` を新設できる。
  前者は display より前の feature、後者は純粋な leaf とする。新設時は
  `PROJECT.md` の依存順と `web/index.html` の modulepreload を更新する。
- `scripts/test-horizontal-scroll.mjs`: ブラウザで実表示を検証する再実行可能な検査。

サーバ・CLI・JSON契約・1列表示の動作・配布設定・仕様本文は変更しない。
着手元には別途CSSの応急修正とユーザー画像が未コミットで残っているが、この作業は
仕様コミットから作った別worktreeで行う。元のworktreeを変更・コミットしない。

## 順序と検証の対応

手順1で状態の寿命と計算を固定し、手順2で表示と入力を接続する。
手順3で実ブラウザ・大規模データとリリースビルドを確認する。
すべて `R-VIEW-HSCROLL` を検証し、手順2・3は `R-VIEW` / `R-LIVE` の
既存の縦位置保持と `R-WS` の層も確認する。
命名、内部の関数分割、テストデータの具体的な文字列は実装判断に任せる。
仕様にない利用者向け動作の変更、新しい外部依存、性能要件の緩和が必要なら戻す。
マージ、push、リリースは行わない。最後の表示確認はcycleの完了時にまとめる。

## 手順1 — 横状態の境界と寿命

目的: 再描画で失われない横位置と幅を、画面要素に依存せず検証可能にする。
仕様: `R-VIEW-HSCROLL` の保持・復元・計測の条件。
前提: 上記の仕様と既存の表示/ファイル切り替え経路を読む。
変更可: model、state とそのテスト、必要なら上記の純粋な横状態モジュール。
完了条件: 幅の拡大、横位置の上限補正、同一エントリと別エントリ、
再計測の区別について、実際の状態遷移を検証できる。
証拠の種類: test。`node --test web` で新しい動作の失敗を先に確認し、
最小実装後に全件成功させる。テスト名は仕様の動作を表し、内部構造の一致を検査しない。
実装判断: 状態の型と純粋関数の分割。未使用の抽象化は作らない。
戻す条件: 仕様の保持/補正規則だけでは状態遷移を決められない場合。

## 手順2 — 下端の操作部と再描画の統合

目的: バー、横入力、キーボードのどの操作でも表示中のコードを同期させる。
仕様: `R-VIEW-HSCROLL` 全体、`R-VIEW`、`R-LIVE`、`R-WS`。
前提: 手順1が成功していること。
変更可: 上記のフロント変更範囲と `scripts/test-horizontal-scroll.mjs`。
完了条件: 仕様の成功条件を実際のブラウザで確認できる。DOMの再生成、
長短が異なる行、相手の無い行、画面サイズ変更、Wrap・表示モードの往復、
別エントリへの移動、内容更新・テーマ/ハイライトの再計測を検証する。
証拠の種類: test。ブラウザ検査を先に追加し、現行実装で機能不在の失敗を確認する。
実行コマンドは `node scripts/test-horizontal-scroll.mjs`。
検査はインストール済みの `agent-browser` を利用して実際の画面要素・CSSを検証する。
必要なら本物のkemiを一時manifestで起動するか、実製品の描画を呼ぶ専用ページを
ループバックHTTPで配信する。製品の幅計測や描画をテスト用の模造処理に置き換えない。
入力データは架空の文書とコードを使う。ユーザー画像や実環境のパスをコピーしない。
検査用のプロセスは自身が起動したものだけ終了し、一時ファイルはリポジトリ外に置く。
失敗やブラウザ不足を成功扱いでスキップしない。
実装判断: スクロールの反映方法とイベントの所有者、検査用サーバの配信方法。
戻す条件: 一列の動作変更や全行DOM化が必須になる場合、仕様の入力操作を提供できない場合。

## 手順3 — 統合検証と確認用ビルド

目的: 既存の機能を保ち、大規模な差分でも実用的に操作できることを示す。
仕様: `R-VIEW-HSCROLL` の成功条件と `R-VIEW` の50万行・行要素数。
前提: 手順2の単体検査とブラウザ検査が成功していること。
変更可: 検証で見つかった範囲内の不具合と、その検査のみ。各修正はテスト先行。
完了条件: 以下のコマンドが順に成功し、実測と画面の確認結果が残る。
証拠の種類: check。作業worktreeのルートから次の順で実行する。

1. `node --test web`
2. `npm ci` の後、`npx tsc -p web --noEmit`（既存lockfileの開発依存を使用し、
   依存定義とlockfileは変更しない。）
3. `node scripts/test-horizontal-scroll.mjs`
4. `cargo test`
5. `cargo build --release`
6. `git diff --check`

ブラウザ検査には50万行の疎な差分も含め、行要素数が表示付近に収まることと、
縦/横操作後に画面が更新されることを確認する。操作時間と画面寸法を記録し、
固定の未合意ミリ秒閾値は作らない。操作感の最終判断は完成後の人の確認で行う。
実装判断: 既存fixture生成の再利用か、一時manifestの生成。
戻す条件: 検証環境を安全に準備できない場合、仕様の50万行を扱えない場合。
ユーザーが読む確認画面を勝手に終了しない。

## 引き渡し

一関心ごとにコミットし、各手順の失敗→成功の証拠、ビルド結果、実測、
変更範囲外の変更の有無を報告する。実装報告はcycleへ返す。
計画は人が結果を受け入れてマージするまで残す。
